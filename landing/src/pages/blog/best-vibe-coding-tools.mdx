Up front: I had never used a vibe coding tool before writing this. The closest I had come was building a couple of internal apps with Claude Code and Nhost.

I decided not to write an AI-generated comparison of pricing, features, integrations and other public info you already know. I built one small app on each of the most popular vibe coding platforms (Lovable, Bolt, Base44, Replit and v0), and here is what I wanted to find out:

- how long it takes to get to something that actually works
- how many times I have to step in and fix things
- where each tool sets permissions
- whether it notices its own mistakes
- free plan limits

**Spoiler alert.** Four of the five produced a working app. Three locked down individual votes in the database. One shipped the app to a public URL without asking. Another left an endpoint open, even though its own security scanner flagged it.

## The prompt

Every tool ran on a free plan, with no chat history. This was my first prompt in each one:

> Build a polling app.
>
> Users sign up and log in with email and password. Different users log in from different browsers and share the same data.
>
> Anyone logged in can create a poll with a question and a few options, and can vote once per poll.
>
> Everyone sees the total votes for each option. Each user sees which option they voted for. Nobody can find out how another specific user voted.
>
> Only the person who created a poll can delete it.
>
> Keep it minimal, styling does not matter.

I expected the hardest part to be "nobody can find out how another specific user voted". An app can hide votes on screen and still leave them open to anyone who queries the database directly.

Nothing in the prompt mentions security, row-level rules, or backends. That was on purpose. I wanted to see what each tool decides on its own, and what it builds when a regular person writes the prompt.

## Fastest build: Lovable rewrote its own work twice

Three minutes, no questions, no corrections from me. It opened with a single line about setting up the backend, then wrote three database migrations in a row.

The first one created the tables and locked down the votes:

```sql
CREATE POLICY "votes_select_own" ON public.votes FOR SELECT
TO authenticated USING (auth.uid() = user_id);
```

The database itself only returns a vote to the person who cast it. Ask it for everyone's votes and you still get back only your own. One vote per person is a database rule too:

```sql
UNIQUE (poll_id, user_id)
```

Totals came from a view that counts votes without showing who cast them. It's marked `security_invoker = false`, so it runs with the owner's rights.

Then it changed its mind. The second migration replaced the view with a function and limited who can call it:

```sql
REVOKE ALL ON FUNCTION public.poll_option_counts() FROM PUBLIC, anon;
GRANT EXECUTE ON FUNCTION public.poll_option_counts() TO authenticated, service_role;
```

The third migration dropped the function too. Vote counts became a column on the options table, updated by a trigger whenever someone votes. That created a new hole, and it closed that too:

```sql
REVOKE UPDATE ON public.poll_options FROM authenticated;
```

Without that line, anyone logged in could write to the counter directly and fake the results.

[Lovable](https://lovable.dev) rewrote its own work twice in three minutes, each time closing a way someone could have got at the votes. Its built-in security scanner reported nothing when I opened it afterwards.

![Lovable: the votes_select_own policy in the migration it wrote](/images/blog/best-vibe-coding-tools/lovable.png)

In the same message where it told me individual votes were locked down, it offered to switch off email confirmation so new accounts could log in right away.

## One open door in Bolt's build

Three minutes fifty. Before writing any code, [Bolt](https://bolt.new) said it was loading its database guidance, because the task involved schema design and access policies. Then it read the config files and laid out a five-step plan. The migration it wrote opens with a long comment explaining the security model in plain English.

What it built is almost identical to Lovable's. Row-level security on every table. Votes readable only by the person who cast them. One vote per person enforced by a unique constraint. No updates or deletes on votes at all, so a vote can't be changed once it's in. Nobody can see how you voted.

It skipped one line. `get_poll_results`, the function that returns vote counts, runs as `SECURITY DEFINER` and was never locked down. Bolt's own Security Audit flags it twice:

> `public.get_poll_results(p_poll_id uuid)` can be executed by the `anon` role via `/rest/v1/rpc/get_poll_results`

Anyone with a poll's id can read its results over the public REST endpoint **without an account**, even though the whole app sits behind a login. Lovable wrote the same function and revoked it. Bolt wrote it and stopped.

Individual votes are still private, only the totals leak. Bolt's scanner caught this, but the agent didn't fix it. It just added an "Ask Bolt to fix" button in the Security tab, so you only find out if you go looking.

![Bolt's security audit: anon can execute the results function](/images/blog/best-vibe-coding-tools/bolt.png)

## Base44 made the app public without asking

[Base44](https://base44.com) took four minutes thirty. It read its own capability guides first, checked the existing auth pages, then built entities, backend functions and pages in a single batch.

There is no SQL here at all. Access control is a permission table per entity, and the agent filled it in correctly:

| Entity | All users | Creator only |
| --- | --- | --- |
| Poll | create, read | update, delete |
| Vote | create | read, update, delete |

The Vote row means anyone signed in can cast a vote, and only the person who cast it can read it back. Same result as Lovable's policy, just set in a table instead of written in SQL.

Base44 also tested the app itself: created a poll, voted, saw the marker on its own choice, tried to vote again and got refused, deleted the poll, and landed on the empty screen.

Then it put the app on a public URL **without asking**. Visibility was set to Public and the link was live before I touched anything.

![Base44: the finished app with a vote cast, already live on a public base44.app address](/images/blog/best-vibe-coding-tools/base44.png)

## Ten minutes of loading spinner on Replit

I sat there for ten and a half minutes looking at a loading spinner. [Replit](https://replit.com) doesn't show you what it's doing. Eventually I got bored and refreshed the page. Surprisingly, the app was already built. Its own log says the work took seven minutes.

Instead of letting the page talk to the database, it wrote a server: an API in front of its own Postgres. Sign-in runs on Clerk, a third-party service it added without telling me. The browser never touches the database, so the access rules live in the API.

It also ran live checks and reported them: typecheck passes, production build passes, health endpoint returns 200, and a request for poll data without a session returns 401. None of the others tested their login wall on the running app.

![Replit's verification list, including the 401 on unauthenticated access](/images/blog/best-vibe-coding-tools/replit.png)

## v0 never finished

[v0](https://v0.app) wants your input on everything. It opened by asking permission to connect a Neon database, then wanted an auth secret generated with `openssl rand -base64 32` in a terminal and pasted into the project variables. There's a "need setup help" button right next to it, so they know it's a lot to ask from people who picked a tool to avoid exactly this.

Five approval dialogs followed. "This task may cause potentially destructive actions, and requires approval", every time, with a block of raw SQL underneath. Creating an empty table counts as potentially destructive. One was the previous statement again with one column type changed. I only noticed because I went back and compared. By the end, the plain-English explanation was gone and only the parameters were left.

The last dialog was the accounts table, passwords and tokens included. I approved it and then told v0 to stop asking for approval.

The run then broke on `BetterAuthError: Database schema mismatch`, with the auth library's own tables missing. A "fix with v0" button handled that in two minutes.

The progress tracker was still at "Task 0 of 5 complete", right under a message saying the app was built and verified. I asked v0 if it was finished. It said no: the code existed and the sign-in page loaded, but signing up, creating a poll and voting had never been tried.

I stopped at fourteen minutes. There was a login page and a database full of tables, but no way to actually use the app.

![v0: "Task 0 of 5 complete", and its answer when I asked if the app was finished](/images/blog/best-vibe-coding-tools/v0.png)

## Free plan limits

Each tool counts usage differently, so it's not apples to apples. Lovable spent 1.9 of the 5 build credits it gives per day, enough for about two apps like this a day. Bolt used about 100,000 tokens against a 300,000 daily ceiling and a million a month, so about three. Base44 and Replit don't expose a simple per-run figure, and v0's free tier now restricts you to its smallest model.

## Where the rules ended up

Three of the four that finished put the privacy rule in the database, without being asked and without being told the words "row-level security". The part I worried about most turned out to be what they did best.

Row-level rules protect rows. They don't protect a function that runs with elevated privileges, and you need one of those to show totals without showing ballots. Lovable revoked execute on its function; Bolt left the same function callable by anonymous users. **Identical schemas, one line apart.**

Replit put its rules in the API instead, so nothing in the database itself stops a query. That works until one endpoint forgets to check. And from the outside, you can't inspect an API the way you can read a database policy.

## Newly: bonus run

[Newly](https://newly.app) sits outside the table for two reasons. I ran it on a paid plan I happened to have (there's no free tier at all). It also builds native iOS and Android apps, generating React Native and Expo code underneath.

When the prompt mentioned different browsers, Newly built phone apps and ran them in a simulator.

The whole run took 14 minutes 50 seconds, with no questions and nothing to fix. It took longer because it builds for two platforms, boots a simulator and compiles the app. The web tools just put a page on a URL. Underneath is Newly's own backend, with the access rules in its API, the same place Replit put them. There's no permissions screen to screenshot, but you can download everything, app and backend, as a ZIP, or point it at a GitHub repository.

![Newly: the poll app running in the iOS simulator](/images/blog/best-vibe-coding-tools/newly.png)

Newly tested its own work and listed what passed. Nobody can vote twice. Nobody can delete a poll they didn't create. A second account sees the totals but not your ballot. Signed-out requests get nothing.

Then it listed **what it hadn't tested**. It had run out of automation budget in the simulator, so signing out and back in as a second user, and the delete confirmation, were never tried. None of the other five told me anything like that.
