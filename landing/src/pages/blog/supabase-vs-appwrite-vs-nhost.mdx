I picked a bad month to write this. It's October, and all three platforms have been shipping consistently. Launches happen, new releases ship, and sometimes a major release lands right in the middle of writing a draft. Comparisons like this have a shelf life.

So here's what this is: a hands-on comparison in October 2026 of Supabase, Appwrite and Nhost, from building the same small app three times. All three on free plans, all three through the dashboards rather than the CLI. Serious builders lean on the CLI, I know, but the dashboard is where most people form their first opinion of a platform, so that's the lens I'm using.

I work at Nhost, but I've tried to keep this as neutral as possible by running the same test across the board. I intend to be transparent, so I'll mention when I'm repeating a vendor's claims rather than something I checked myself.

## TL;DR

**Supabase** is a better fit for developers who want PostgreSQL at the core of their backend. It's ideal for people who are comfortable with SQL and relational databases and want more direct control over their data and database architecture.

**Appwrite** feels like a classic backend-as-a-service. You work through SDKs and APIs, and the platform hides most of the database and infrastructure from you.

**Nhost** is Postgres plus a GraphQL API generated from your schema, with permissions checked on every request. That makes it a good backend for AI apps: assistants and vector search are built in, and an agent can't see more than the user it works for.

## Supabase vs Appwrite vs Nhost Overview

|  | Supabase | Appwrite | Nhost |

| **What's underneath** | A Postgres you can take elsewhere | Five stores, or a standalone Postgres beside the platform | A Postgres you can take elsewhere |

## What each one actually is, in one picture

```text
 SUPABASE              APPWRITE 2.0                NHOST
 ========              ============                =====

 your app                your app                your app
     |                       |                       |
 PostgREST /            Appwrite API            GraphQL API
Auth / Storage               |                       |
     |              +--------+--------+              |
  POSTGRES        TablesDB  Docs   Vectors        POSTGRES
(the product)      (managed by Appwrite)        (the product)

                  ...and off to the side,
                  no Appwrite in the path:
                     NATIVE PG / MySQL
```

**Supabase** is Postgres with services generated around it. PostgREST exposes your tables as REST, auth users live in an `auth` schema, storage keeps file metadata in a table. Permissions are row-level security policies: SQL that sits in the database and runs on every query, whatever issued it.

**Appwrite** is an API layer with storage engines behind it. Requests go to Appwrite, which resolves them against TablesDB, DocumentsDB or VectorsDB. Permissions are grants attached to tables and rows, enforced by Appwrite on the way through. Since 2.0 you can also provision a standalone Postgres or MySQL and point a driver at it directly, which skips both the API and the permissions.

**Nhost** is Postgres with a GraphQL API generated from the schema. One endpoint serves queries, mutations and subscriptions, and the client introspects the types. Permissions are per-role rules stored as metadata rather than SQL, and Auth, Storage and Functions read the same session variables, so one rule covers a query, a subscription and a file download.

## Data modeling

This used to be an easy choice between Postgres and documents. Now all three offer Postgres in some form, so that's no longer what sets them apart.

### Supabase: one store, and you extend it

You get Postgres. When you need something Postgres doesn't do natively, you can install an extension. Vectors are `pgvector`. Queues are `pgmq`. Cron is `pg_cron`. Geospatial is PostGIS. Full-text search is built in.

The upside is that everything lives in one place with one consistency model and one backup. You can join your embeddings against your users in a single query, and nobody has to think about which system owns which record.

The downside is that everything shares one database. Vectors, queues and cron jobs all compete for the same server, and Postgres limits how many connections it accepts at once. That's true of any Postgres-based platform.

### Appwrite: five stores, and you pick per workload

Appwrite 2.0 added four new stores, so the full list now looks like this:

- **TablesDB**: structured data with relations, queried through Appwrite's API rather than SQL.
- **DocumentsDB**: schemaless JSON (Beta).
- **VectorsDB**: embeddings and similarity search. You set the vector size when you create the collection (Beta).
- **Native Postgres**: a standard Postgres, outside Appwrite's permissions and realtime.
- **Native MySQL**: the same, for MySQL.

The Databases page only lets you create three of these: TablesDB, DocumentsDB and VectorsDB. Native Postgres and MySQL aren't there. They do show up in the Explorer, Appwrite's in-console API client, where the PostgreSQL service alone has 33 endpoints. So they exist, but on my plan you reach them through the API, not the dashboard.

The free plan caps you at one database, so I couldn't create a second to try another type.

![Appwrite's Databases page: three creatable types, DocumentsDB and VectorsDB in beta.](/images/blog/supabase-vs-appwrite/appwrite-database-types.png)

### Nhost: Postgres, with the API generated from it

Your data lives in a standard Postgres with full SQL access. Extensions install the usual way, with `CREATE EXTENSION` in a migration: pgvector, PostGIS, pg_cron, uuid-ossp, pg_trgm. When you create a table, Nhost reads the schema and generates a typed GraphQL API for it, with filters, ordering, pagination, aggregates and live subscriptions.

You choose which tables go into the API. The SQL editor has a "Track this" toggle, and a table created without it exists in Postgres but not in your API. It works like the permissions: nothing is reachable until you allow it.

### Relations: a constraint versus a field

I linked posts to authors, and each platform handles that link differently.

In **Supabase** a relation is just a foreign key:

```sql
alter table public.posts add constraint posts_author_id_fkey
  foreign key (author_id) references public.authors (id);
```

That one statement does two jobs. It stops a post from pointing to an author who doesn't exist, and it lets PostgREST turn `.select('*, authors(name)')` into a join, because the API reads your foreign keys.

**Appwrite** treats relation as a column type you set up in a form. Creating one asked me five things, in this order:

1. One-way or two-way
2. Which table to link to
3. What to call the column on each side
4. The cardinality: one-to-one, one-to-many, many-to-one or many-to-many
5. What happens on delete: Set NULL, Cascade or Restrict

That's five decisions up front instead of one statement, though the form does show a plain-English summary of your choices.

The console also warns that the column key on the related side can't be renamed later. In Postgres you can drop and recreate a foreign key whenever you like.

With **Nhost**, a relation is a foreign key plus a name. You write the constraint in SQL as usual, then give the link a name for the API. The dashboard spots your foreign keys and lists them under **Suggested Relationships** with the names already filled in. One click and `author { name }` works. You can nest it as deep as you want, and it all comes back in one request, with no join to write in each query.

![Nhost's Edit Relationships panel: the author relation created from a foreign key.](/images/blog/supabase-vs-appwrite/nhost-relationships.png)

### The API layer

Here's the same query on all three. Supabase wraps SQL in a chain of methods, Appwrite gives you SDK calls with query helpers, and Nhost gives you GraphQL, where you write the shape of the response yourself.

**Supabase:**

```ts
const { data, error } = await supabase
  .from('posts')
  .select('id, title, author:authors(name)')
  .eq('published', true)
  .order('created_at', { ascending: false })
  .limit(20)
```

That `author:authors(...)` bit is a join, resolved by PostgREST because it can see the foreign key I added earlier. Once the syntax clicks it's fast to write, but until then the error messages don't help much.

New tables in the `public` schema are no longer exposed to it automatically, and that becomes mandatory for every project on October 30th, 2026. I checked a project created before the cutover, and the old behavior is still live. "Automatically expose new tables" was on, and two tables I'd just made in SQL were already answering on the REST endpoint. I never touched the setting.

Supabase also no longer enables `pg_graphql` automatically, and introspection is off by default for new projects since 1.6.0. If you want GraphQL on Supabase, you have to turn it on yourself.

![Supabase's Data API settings, with "Automatically expose new tables" still on.](/images/blog/supabase-vs-appwrite/supabase-data-api-settings.png)

**Appwrite:**

```ts
import { TablesDB, Query } from 'appwrite'

const tablesDB = new TablesDB(client)

const rows = await tablesDB.listRows({
  databaseId: 'main',
  tableId: 'posts',
  queries: [
    Query.equal('published', [true]),
    Query.orderDesc('$createdAt'),
    Query.limit(20),
  ],
})
```

Note the `$createdAt`. Appwrite adds `$id`, `$createdAt` and `$updatedAt` to every row on its own, and the dollar sign shows which fields belong to Appwrite.

**Nhost:**

```ts
import { createClient } from '@nhost/nhost-js'

const nhost = createClient({ subdomain, region })

const resp = await nhost.graphql.request({
  query: `query {
    posts(
      where: { published: { _eq: true } }
      order_by: { created_at: desc }
      limit: 20
    ) {
      id
      title
      author { name }
    }
  }`
})

console.log(resp.body.data?.posts)
```

`author { name }` follows the link from each post to its author and returns just the name, nested inside the post. Go one level deeper and it's still a single request.

The schema is typed, so your editor can autocomplete fields and flag a wrong field name before you run anything. AI agents get the same help: they can read the schema first and see which tables and fields exist before they write a query.

## Auth

All three have a solid provider list, MFA and OIDC, and each can act as an identity provider for other applications.

**Supabase** added passkeys in beta (WebAuthn, biometrics, device PIN, or a hardware key) and OAuth 2.1 authorization-server capabilities, so your project can issue tokens to third-party apps and MCP clients. Auth users live in a Postgres table, which makes custom claims, triggers, and joins against your own tables easy. It also means a badly written trigger on signup can break sign-ups entirely.

With **Appwrite 2.0**, you host the OAuth consent screen yourself, so users approving access stay on a page that looks like your product. Client registration is also an API call in the client SDKs, which lets you build a self-serve portal where other developers register their own apps. Both only help if other developers will build on top of your app.
**Nhost Auth** handles email and password, magic links, one-time codes, WebAuthn and social sign-in, with MFA and OIDC. Users live in a Postgres table in the `auth` schema, so linking a user to their own rows is an ordinary foreign key, and any custom claim you define becomes a permission variable available inside every rule you write.

**Nhost Auth** handles email and password, magic links, one-time codes, WebAuthn and social sign-in. Users live in a Postgres table in the `auth` schema, so you link a user to their rows with a regular foreign key. Any custom claim you add to a user can be used in your permission rules.

## Authorization rules

Authorization rules decide who can read and change which rows. To compare them, I wrote the same four rules for the `posts` table in my test app. Each post has a `title`, a `body`, a `published` flag and an author.

1. Anonymous visitors see only posts where `published` is true
2. Signed-in users can create posts
3. Authors can edit and delete only their own
4. Nobody else's drafts are visible to anyone

I tested rules 1 and 4 on all three platforms. Rules 2 and 3 are set up on all three too, but I didn't test them end to end, since that needs real user accounts.

**Supabase** covers published posts and private drafts with two policies:

```sql
create policy "anyone reads published posts"
on public.posts for select using (published = true);

create policy "authors read their own drafts"
on public.posts for select to authenticated using (auth.uid() = author_id);
```

I ran `select title, published from posts` as the Anonymous role in the dashboard. One row came back out of two, and the draft didn't show up.

![Run as Anonymous in Supabase: one row back, the draft hidden.](/images/blog/supabase-vs-appwrite/supabase-run-as-anonymous.png)

**Appwrite** can't express "anonymous visitors see only published posts" at all, and this was the biggest difference I found. Its permission roles only describe who you are: Any, All guests, All users, a specific user or a team. There's nowhere to add a condition on the row's data, like `published = true`. You could filter by `published` in the query, but the caller can just leave that filter out. A permission applies either way.

Here's the workaround I used:

1. Remove Any → Read at the table level. Leave it on and every draft is world-readable, because table permissions override row permissions.
2. Enable Row security.
3. On the published row, add Any → Read by hand.
4. On the draft, add only `user:demo-author-1` with read, update, delete.

![Appwrite row permissions: the draft's access granted to one user by hand.](/images/blog/supabase-vs-appwrite/appwrite-row-permissions.png)

It works, but now the `published` column doesn't do anything. What actually publishes a post is a permission you have to add to each row when you create it. Forget it on a published post and nobody sees it. Add it to a draft by mistake and the draft goes public. In Supabase there's nothing to forget, because the rule is written once for the whole table.

It also gets hard fast as rules get more complex. Something like "users can read orders in their org, unless the order is archived, unless they're an admin" is four lines of SQL in Supabase. In Appwrite you'd have to redesign your data model to fit it.

Appwrite's native Postgres has no permissions at all, since requests go straight to the database and never pass through Appwrite. You'd have to write your own middleware or set up RLS yourself with your own JWTs. 

Three roadblocks I hit in Appwrite that aren't in the docs:

- Row permissions are invisible from the row. Open a row to edit it and you see the data fields only. Permissions live in the `...` menu under "Manage permissions." Looking at a record tells you nothing about who can read it.
- Row-level permissions have no Create, only Read, Update, Delete. Logical, briefly confusing.
- Custom permissions aren't validated. The field takes `user:[USER_ID]`, `team:[TEAM_ID]/[ROLE]`, or `member:[MEMBERSHIP_ID]` as free text. I typed a user ID that doesn't exist and it saved without complaint. A typo here is a silently broken rule.

### Nhost: the rule is a form

In **Nhost** you can limit visitors to published posts without SQL and without per-row permissions. In the permissions editor you pick the role and the action, then build the condition from three dropdowns:

```text
published   _eq   true
```

![Nhost's permission rule builder: published equals true, built from dropdowns.](/images/blog/supabase-vs-appwrite/nhost-rule-builder.png)

Underneath that's `{"published": {"_eq": true}}`, and the editor will show you either view. The rule that lets authors edit only their own posts looks the same, with the user's ID in place of a fixed value:

```json
{"author_id": {"_eq": "X-Hasura-User-Id"}}
```

The playground has the same role switch the other two have. Set ROLE to `public`, run the query, and:

```json
{ "data": { "posts": [
    { "title": "Hello from Nhost", "published": true }
] } }
```

![Nhost's GraphQL playground as the public role: one row back, the draft hidden.](/images/blog/supabase-vs-appwrite/nhost-run-as-public.png)

OOne row came back out of two, and the draft stayed hidden.

The rule is stored as metadata next to your schema and versioned with your migrations. Nhost applies it to every way into that table: queries, subscriptions, file downloads, and AI assistants acting for a user. You write it once and don't have to repeat it for each endpoint.

By default, access is denied. No role except `admin` can read anything until you grant it. If you create a table and forget to set permissions, it stays private, so nothing leaks by accident.

![Nhost's permissions matrix: roles down the side, actions across the top.](/images/blog/supabase-vs-appwrite/nhost-permissions-matrix.png)

### Testing what a role can see

All three platforms let you check what a given role can see.

On **Supabase**, don't look for something called "RLS Tester". I did, and there's no such panel in the policy editor. Instead, the SQL editor has a role switcher: the dropdown next to Run offers postgres, Anonymous and Authenticated (with a user picker and an MFA level). It also warns you that postgres bypasses RLS.

The shield button on the Policies page doesn't test anything. It opens the AI Assistant, which can write a policy for you. The same page also offers to install a trigger that turns on RLS for every new table, but it's off by default.

On **Appwrite**, it's in a place I didn't expect: the Explorer. Pick TablesDB → List rows, fill in the database and table IDs, and you'll see an Act as: Guest / User toggle right above the Send button. I ran it as Guest against my table and got back this:

```json
{
  "total": 1,
  "rows": [
    {
      "title": "Hello from Appwrite",
      "body": "Public post, visible to everyone."
    }
  ]
}
```

One row out of two, 200 OK in 202 ms, and the draft stayed hidden. This check goes through a real HTTP request, so it shows exactly what a client would get.

![Appwrite's Explorer: an in-console API client with an Act as Guest / User toggle.](/images/blog/supabase-vs-appwrite/appwrite-explorer.png)

On **Nhost**, the role switch sits next to Run in the GraphQL playground. Switch it and the same query runs again under the new role. There's no separate client and no headers to set.

### Which permission model fits

The real difference is what a rule can check. In **Supabase** a rule can check anything SQL can, but you have to write and maintain the SQL policies yourself. In **Appwrite** a rule can only check who the user is. That's easy for the whole team to read, but it stops working once access depends on what's in the row. In **Nhost** a rule can check both who the user is and what's in the row, and you build it in a form. That covers most apps, though not the most unusual cases.

Look at the hardest access rule in your app. If your permission system can't express it, you'll end up writing that check somewhere worse: in the client, in a wrapper endpoint, or on every row by hand.

## Storage

All three now support the S3 API, so you can use standard S3 tools with any of them.

**Supabase** splits egress (outgoing traffic) into cached and origin tiers. Cached egress costs $0.03/GB, about a third of origin. I took that number from [their changelog](https://supabase.com/changelog/38119-3x-cheaper-egress-for-cache-hits), not their pricing page, so check it before you commit. If you serve a lot of images, making sure they come from the cache will noticeably cut your bill.

**Appwrite** says its S3 API works with your existing buckets, so files you upload with the AWS CLI show up in the console, and the other way around. That's from [their 2.0 announcement](https://appwrite.io/blog/post/announcing-appwrite-2). I stayed in the dashboard and didn't test it myself.

In **Nhost**, every upload and download goes through an API that checks the same permission rules as your tables. It also saves file metadata in Postgres and can resize or convert images on download. Presigned URLs, per-file permissions and CDN delivery are included. One set of rules covers both rows and files.

For most apps, the real differences are CDN speed, image transformations and upload limits. Don't trust vendor benchmarks here. Test with the file sizes your app actually uses.
## Functions, and the runtime arms race

| Capability | Supabase | Appwrite | Nhost |
| --- | --- | --- | --- |
| Runtime | Deno 2.1, all regions | Node, Bun 1.4, Deno, Python, PHP, Ruby, Rust, and more | JavaScript and TypeScript, plus any container via Run |
| Deploy | CLI, dashboard, Management API | CLI, console, Git triggers | Git push, CLI |
| Language freedom | TypeScript/JavaScript | Wide | Narrow in Functions, unlimited in Run |

**Appwrite** supports the most runtimes of the three. On August 20th it added [Bun 1.4](https://appwrite.io/blog/post/announcing-bun-1-4-runtime), both for functions and as a build runtime for Appwrite Sites. It's the first Bun version written in Rust instead of Zig. Appwrite says builds are 22% faster than on Bun 1.3, measured on a Next.js app with 640 packages. That's a vendor benchmark on a single workload, so treat it with caution.

**Supabase** gives you one runtime, which means one set of behaviors to learn. For webhooks and glue code, that's plenty. If your pipeline has a Python ML step, it's a dealbreaker.

**Nhost** splits this into two products. Functions run JavaScript and TypeScript and deploy automatically when you push to the connected GitHub repo. They handle HTTP endpoints, event triggers, cron triggers and one-off scheduled events. For anything else there's Run, which deploys any Docker container next to your stack: Go, Python, Rust, or anything that builds into an image. You pay for the vCPU and memory you allocate.

About cold starts: I'm not publishing numbers from a free tier, because they say little about production. Measure your own. Call your function 20 times after five idle minutes and check the p95.

## Realtime

**Supabase Realtime** sends database changes over WebSockets and controls channel access with RLS policies. [Since June 2026, Broadcast also supports binary payloads](https://supabase.com/changelog/46834-realtime-broadcast-now-supports-binary-payloads), which cuts JSON overhead if you're pushing sensor data or image frames. You can now set the connection pool size and max concurrent clients per project, which you'll need once traffic grows.

**Appwrite** realtime uses the same permissions as your data, so a client subscribed to a table only sees rows it's allowed to see. Version 1.9.5 added a [Presences API](https://appwrite.io/blog/post/announcing-presences-api) for online, typing and activity states, a feature most teams end up building themselves. Appwrite's native Postgres has no realtime at all.

**Nhost** does realtime with GraphQL subscriptions. Take any query, change `query` to `subscription`, and you get a live stream over a WebSocket. The same permission rules apply, so a subscribed client only gets the rows its role is allowed to see.

## The AI in the console

Supabase and Appwrite both have an AI assistant in the dashboard, on the free tier. They use it for different things.

**Supabase** puts it on the Policies page. Its suggested prompts include "Set up RLS policies," "Query your data" and "Create a function." It's there to help with access rules, the part that's easiest to get wrong.

**Appwrite** uses it to help you get started. When you create a table, it offers "Smart column suggestions" based on the table name. An empty table shows "Suggest columns" and "Generate sample data" buttons right next to "Create column."

Both help you build your app. Neither becomes part of it.

**Nhost** puts AI inside the app itself, through a product called [Graphite](https://docs.nhost.io/products/ai/). It has two parts:

- **Auto-Embeddings** creates and updates embeddings as rows are added or changed. For each source you set up, it adds two queries to your schema: one for natural-language search and one for finding similar items.
- **AI Assistants** lets you create an assistant and choose which tools it can use: specific GraphQL queries, mutations or webhooks. It can read data, write data or trigger a function, but only through the tools you give it.

Both follow the same permission rules as any other request, so an assistant can only see what the signed-in user can see.

## So which one

I know it's a cliché, but there's no single answer to which one is best. I built one small app on free plans, and a full picture would take running a real production app on each. But it did show the differences you hit on day one: how you link tables, how you write access rules, and what your API looks like.

**Supabase** is for you if you open a SQL editor before you open the docs. Your app's hard part is the data: reports, joins, analytics, logic you'd happily write in Postgres. Supabase lets you keep all of that in the database, as long as someone on the team owns the policies.

You're building a mobile app or a frontend-heavy product, and you'd like to never think about the database. Each user owns their own data, maybe shares it with a team. That's where **Appwrite** feels easiest: login, files, push notifications and hosting all sit in one console.

You want AI agents to work inside your app on your users' behalf, through Claude, ChatGPT or your own assistant. That's where **Nhost** is furthest ahead. Its MCP service signs agents in through Nhost Auth, so every call runs as that user, with that user's permissions. Graphite adds search and assistants under the same rules.
