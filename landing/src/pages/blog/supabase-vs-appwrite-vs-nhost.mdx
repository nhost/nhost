I picked a bad time to write this. All three platforms have been shipping fast, and a few things changed between my first tests in September and publishing this in October. The basics I tested, how each one handles data, permissions and APIs, change slowly, though, and where something has moved since, I say so.

So here's what this is: a hands-on comparison of Supabase, Appwrite and Nhost, from building the same small app three times in September 2026 and rechecking a few details in early October. All three on free plans, all three through the dashboards rather than the CLI. Serious builders lean on the CLI, I know, but the dashboard is where most people form their first opinion of a platform, so that's the lens I'm using. A few things I mention need a paid plan, so I couldn't try them: Appwrite's DocumentsDB, VectorsDB, native Postgres and MySQL, and on Nhost, the AI service, Nhost Run and hosting the MCP server.

I work at Nhost, so read this as an informed but interested view. I ran the same test on all three, and I keep what I tested apart from what I took from docs and changelogs. The data modeling, API and permissions sections come from my own testing, with dates and details checked against the docs. ## TL;DR

Supabase is a better fit if you want to do everything in SQL. You get Postgres with a REST API generated from your schema, and your access rules are row-level security policies that Postgres enforces itself. It works if you're comfortable writing and maintaining those policies.

Appwrite feels like a classic backend-as-a-service. You work through SDKs and APIs, and the platform hides most of the database and infrastructure from you. Its permissions say who can reach a table or a row, but they can't look at what's in the row.

Nhost is also Postgres, but the API it generates from your schema is GraphQL, and you build access rules per role in a form. For AI apps it has a ready-made MCP server that gives an agent your GraphQL API as the signed-in user, plus managed embeddings and assistants. On Nhost Cloud those AI parts need a paid plan, so I didn't test them here. Supabase and Appwrite can sign an agent in as a user too, but you write the MCP tools yourself.

|  | Supabase | Appwrite | Nhost |
| --- | --- | --- | --- |
| **What's underneath** | A Postgres you can take elsewhere | Three stores managed by Appwrite (only TablesDB on the free plan), plus native Postgres or MySQL on paid plans | A Postgres you can take elsewhere |

## What each one actually is, in one picture

```text
 SUPABASE              APPWRITE 2.0                NHOST
 ========              ============                =====

 your app                your app                your app
     |                       |                       |
 PostgREST /            Appwrite API            GraphQL API /
Auth / Storage               |                  Auth / Storage
     |              +--------+--------+              |
  POSTGRES        TablesDB  Docs*  Vectors*       POSTGRES
(the product)      (managed by Appwrite)        (the product)

                  ...and off to the side,
                  with no Appwrite in the path:
                     NATIVE PG* / MySQL*

                  * paid plans only
```

Supabase builds everything on top of Postgres, so your tables, your users and the records of your files all live in one database. Permissions are SQL rules called row-level security (RLS), and Postgres checks them on every query to decide which rows each user gets back.

Appwrite puts its own API in front of the database, so your app never talks to the database directly. You set permissions on tables and rows, and Appwrite checks them on every request. The exception is Appwrite's native Postgres and MySQL, which your server connects to directly, so Appwrite's permissions don't apply there.

Nhost is built on Postgres too, with your users and file records in the same database, and it turns your schema into a GraphQL API, so every table you add to the API gets its own queries, mutations and subscriptions. You write permission rules per role, and the GraphQL API checks them on every request: queries, live updates, and AI assistants acting for a user. Files get their own rules, written in the same editor. Because the rules live in the API rather than in Postgres, a direct database connection skips them.

## Data modeling

All three offer Postgres now, but not on the same terms. Supabase and Nhost have been built on it since day one. Appwrite [added a standalone Postgres](https://appwrite.io/blog/post/appwrite-now-speaks-postgresql) in September 2026, on paid plans only. The difference is in what each one builds around the database.

### Supabase: one store, and you extend it

You get Postgres. When you need something Postgres doesn't do natively, you can install an extension. Vectors are `pgvector`. Queues are `pgmq`. Cron is `pg_cron`. Geospatial is PostGIS. Full-text search is built in.

The upside is that everything lives in one place with one consistency model. You can join your embeddings against your users in a single query, and nobody has to think about which system owns which record. (File contents are the exception: they sit in object storage, and only their records live in Postgres.)

The downside is that everything shares one database. Vectors, queues and cron jobs all compete for the same server, and Postgres limits how many connections it accepts at once. That's true of any Postgres-based platform, Nhost included.

### Appwrite: separate databases for tables, documents and vectors

Appwrite 2.0 added four new stores, so the full list now looks like this:

- **TablesDB**: structured data with relations, queried through Appwrite's API.
- **DocumentsDB**: schemaless JSON (Beta).
- **VectorsDB**: embeddings and similarity search, with built-in models that can generate the embeddings for you. You set the vector size when you create the collection (Beta).
- **Native Postgres**: a standard Postgres, outside Appwrite's permissions and realtime.
- **Native MySQL**: the same, for MySQL.

On the Databases page, the type filter lists three types: TablesDB, DocumentsDB and VectorsDB. On the free plan only TablesDB can be created, because Appwrite runs DocumentsDB, VectorsDB, native Postgres and MySQL as paid dedicated instances, from $10 a month per database. The native engines do show up in the Explorer (Appwrite's in-console API client, where the PostgreSQL service alone has 37 endpoints).

The free plan caps each project at one database, so I couldn't create a second one to try another type.

![Appwrite's Databases page on the free plan: the type filter lists TablesDB, DocumentsDB (beta) and VectorsDB (beta), and the one-database limit is already reached.](/images/blog/supabase-vs-appwrite/appwrite-database-types.png)

### Nhost: Postgres, with the API generated from it

Your data lives in a standard Postgres with full SQL access. Extensions install with `CREATE EXTENSION` in the SQL editor or a migration, after a `SET ROLE postgres;` line as Nhost's docs show: pgvector, PostGIS, pg_cron, uuid-ossp, pg_trgm. When a table is added to the API, Nhost reads the schema and generates a typed GraphQL API for it, with filters, ordering, pagination, aggregates and live subscriptions. The engine underneath is Hasura, and aggregates are something you switch on per role. Supabase's REST API has filters, ordering and pagination too, plus aggregates you can switch on. The difference is that on Nhost it's all one GraphQL schema, live subscriptions included.

You choose which tables go into the API. Tables you create in the table editor go in automatically. The SQL editor has a "Track this" toggle, off by default, and a table you leave out gets a "Track now" button in the table view. Being in the API doesn't make a table readable, though: until you add a permission, only admin can query it.

### Relations: a constraint versus a field

I linked posts to authors, and each platform handles that link differently.

In Supabase a relation is just a foreign key:

```sql
alter table public.posts add constraint posts_author_id_fkey
  foreign key (author_id) references public.authors (id);
```

That one statement does two jobs. It stops a post from pointing to an author who doesn't exist, and it lets PostgREST turn `.select('*, authors(name)')` into a join, because the API reads your foreign keys.

Appwrite treats a relation as a column type you set up in a form. Creating one asked me five things:

1. One-way or two-way
2. Which table to link to
3. What to call the column on each side
4. The cardinality: one-to-one, one-to-many, many-to-one or many-to-many
5. What happens on delete: Set NULL, Cascade or Restrict

That's five fields up front, though the form starts on one-way and fills in the column name, so the real choices are the table, the cardinality and what happens on delete. The SQL version names the table and column and quietly takes defaults for the rest, like what happens on delete. The form does show a plain-English summary of your choices.

The console also warns that the column key on the related side can't be renamed later. In Postgres you can drop and recreate a foreign key whenever you like.

With Nhost, a relation is a foreign key plus a name. You write the constraint in SQL as usual, then give the link a name for the API. The dashboard spots your foreign keys and lists them under "Suggested Relationships" with the names already filled in. Click Add, confirm the name, and `author { name }` works (other roles also need read access to `authors`). You can nest it several levels deep and it all comes back in one request. Supabase's embedded selects do the same. The difference is that on Nhost you name the relationship once, while PostgREST works it out from the foreign key in each query.

![Nhost's Edit Relationships panel: the author relation created from a foreign key.](/images/blog/supabase-vs-appwrite/nhost-relationships.png)

### The API layer

Here's the same query on all three: the 20 newest published posts, each with its author's name. Supabase and Appwrite build it from method calls and query helpers, and Nhost gives you GraphQL, where the query has the same shape as the response.

**Supabase:**

```ts
const { data, error } = await supabase
  .from('posts')
  .select('id, title, author:authors(name)')
  .eq('published', true)
  .order('created_at', { ascending: false })
  .limit(20)
```

That `author:authors(...)` bit is a join, resolved by PostgREST because it can see the foreign key I added earlier. Once the syntax clicks it's fast to write, but until then the error messages don't help much.

Supabase is changing what gets exposed, but more slowly than it announced. Its [changelog](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically) says new tables in the `public` schema stop being exposed to the API automatically: on new projects in a gradual rollout from May 30th, 2026, and on all existing projects from October 30th, 2026. Tables you already have keep their grants. The first step hasn't fully landed, and in late August [Supabase's CLI](https://github.com/supabase/cli/releases/tag/v2.116.0) went back to exposing new tables by default, to match how cloud projects still behave. My test project still had the old behavior. "Automatically expose new tables" was on, and two tables I'd just made in SQL were already answering on the REST endpoint. I never touched the setting. On a project like that, a table made in SQL is open to anyone with the public key until you turn on RLS. Tables made in the Table Editor have RLS on by default either way.

Supabase also no longer enables `pg_graphql` automatically, and since [version 1.6.0](https://supabase.com/changelog/46320-breaking-change-in-pg-graphql-1-6-0-graphql-introspection-disabled-by-default) of the extension, introspection is off by default for new projects. Supabase made both changes to shrink what someone holding the public key can learn about your schema. If you want GraphQL on Supabase, you have to turn it on yourself. So Supabase generates an API from your schema too. It's just REST first, and GraphQL is now something you opt into.

![Supabase's Data API settings, with "Automatically expose new tables" still on.](/images/blog/supabase-vs-appwrite/supabase-data-api-settings.png)

**Appwrite:**

```ts
import { TablesDB, Query } from 'appwrite'

const tablesDB = new TablesDB(client)

const rows = await tablesDB.listRows({
  databaseId: 'main',
  tableId: 'posts',
  queries: [
    Query.select(['$id', 'title', 'author.name']),
    Query.equal('published', [true]),
    Query.orderDesc('$createdAt'),
    Query.limit(20),
  ],
})
```

Note the `$createdAt`. Appwrite adds `$id`, `$createdAt` and `$updatedAt` to every row on its own, and the dollar sign shows which fields belong to Appwrite. Appwrite also doesn't load related rows unless you ask, so the author's name comes from `author.name` in `Query.select`. Without it, the response has no author name. Relations nest up to three levels in one request.

Appwrite has a GraphQL endpoint too, but it's generic: every row comes back as the same type, with your columns packed into one JSON string, so you don't get a schema per table.

**Nhost:**

```ts
import { createClient } from '@nhost/nhost-js'

const nhost = createClient({ subdomain, region })

type Post = { id: string; title: string; author: { name: string } | null }

const resp = await nhost.graphql.request<{ posts: Post[] }>({
  query: `query {
    posts(
      where: { published: { _eq: true } }
      order_by: { created_at: desc }
      limit: 20
    ) {
      id
      title
      author { name }
    }
  }`,
})

console.log(resp.body.data?.posts)
```

`author { name }` follows the link from each post to its author and returns just the name, nested inside the post. Go one level deeper and it's still a single request, as it is with Supabase's nested selects.

GraphQL is typed and introspectable, so tools can read the schema straight from the endpoint. A GraphQL editor plugin uses the schema to autocomplete fields and flag a wrong field name in queries tagged with `gql` or `graphql`. GraphQL Code Generator checks your queries against the schema and writes their result types for you. Without it, you write the result type by hand, as in the snippet above. Supabase and Appwrite get the same kind of help from types their CLIs generate.

The difference shows up at runtime. On Nhost, any role can read the part of the schema it's allowed to query, so an agent working for a user can see which tables and fields exist before it writes a query. Supabase no longer shows its schema to the public key, on purpose, so your API is harder to map.

## Auth

All three have a solid provider list and MFA, and each can act as an OAuth2 and OpenID Connect provider for other applications. One gap on Nhost: Supabase and Appwrite can also sign users in through any OIDC provider you configure, while Nhost supports its built-in list, with enterprise SSO going through WorkOS or Entra ID.

Supabase added passkeys (WebAuthn, biometrics, device PIN, or a hardware key) and an OAuth 2.1 authorization server, so your project can issue tokens to third-party apps and MCP clients. Both are still in beta. Auth users live in a Postgres table, which makes custom claims, triggers, and joins against your own tables easy. It also means a badly written trigger on sign-up can break sign-ups entirely, which Supabase's docs warn about.

Appwrite 2.0 added an OAuth2 server, so a project can act as an OAuth 2.1 and OpenID Connect provider. As on Supabase and Nhost, you build and host the consent screen yourself, so users approving access stay on a page that looks like your product. Appwrite also exposes client registration in its client SDKs, so any signed-in user can register an app, which is handy if you want a self-serve developer portal. The same server lets MCP clients like Claude Code sign in to your app as a specific user. Its tokens aren't Appwrite sessions, though, so your MCP server decides what that user can reach: it can call Appwrite with a JWT made for that user, or use an API key and filter by user ID, as Appwrite's own example does.

Nhost Auth handles email and password, magic links, one-time codes, WebAuthn and social sign-in. Users live in a Postgres table in the `auth` schema, so you link a user to their rows with a regular foreign key. Any custom claim you add to a user can be used in your permission rules.

## Authorization rules

Authorization rules decide who can read and change which rows. To compare them, I wrote the same four rules for the `posts` table in my test app. Each post has a `title`, a `body`, a `published` flag and an author.

1. Anonymous visitors see only posts where `published` is true
2. Signed-in users can create posts
3. Authors can edit and delete only their own
4. Nobody else's drafts are visible to anyone

I tested rule 1, and the signed-out half of rule 4, on all three platforms. Rules 2 and 3 are set up on all three too, but I didn't test them end to end, since that needs real user accounts.

Supabase covers published posts and private drafts with two policies, once RLS is on for the table:

```sql
alter table public.posts enable row level security;

-- projects that don't expose new tables automatically also need a grant
grant select on public.posts to anon, authenticated;

create policy "anyone reads published posts"
on public.posts for select using (published = true);

create policy "authors read their own drafts"
on public.posts for select to authenticated using (auth.uid() = author_id);
```

I ran `select title, published from posts` as the Anonymous role in the dashboard. One row came back out of two, and the draft didn't show up.

![Run as Anonymous in Supabase: one row back, the draft hidden.](/images/blog/supabase-vs-appwrite/supabase-run-as-anonymous.png)

Appwrite can't express "anonymous visitors see only published posts" as a single rule, and this was the biggest difference I found. Its permission roles only describe who you are: Any, All guests, All users, a specific user, a team or a role in it, or a user label. There's nowhere to add a condition on the row's data, like `published = true`. You could filter by `published` in the query, but the caller can just leave that filter out. A permission applies either way.

Here's the workaround I used:

1. Remove Any → Read at the table level. Leave it on and every draft is world-readable, because Appwrite lets a caller in if either the table or the row grants access.
2. Enable Row security.
3. On the published row, add Any → Read by hand.
4. On the draft, add only the author, with Read, Update and Delete.

![Appwrite row permissions: the draft's access granted to one user by hand.](/images/blog/supabase-vs-appwrite/appwrite-row-permissions.png)

It works, but now the `published` column doesn't decide who can read the post. The Any → Read grant on the row does. Drafts are private without extra work, because a row an author creates from the client SDK is readable only by that author by default. But publishing means adding the Any → Read grant in the same update that flips `published`, and unpublishing means removing it. Forget it and visitors never see the post. Add it to a draft by mistake and the draft goes public. In Supabase the policy reads the column, so there's only one thing to change.

It also gets hard fast as rules get more complex. Something like "users can read orders in their org, unless the order is archived, unless they're an admin" is four lines of SQL in Supabase. In Appwrite you'd model each org as a team, make admins a team role, and have your code swap each order's read grant when it's archived, because no rule can look at the `archived` column.

Appwrite's permission system doesn't reach its native Postgres. You connect with Postgres credentials and there's no Appwrite API in between, so access control is whatever you set up in Postgres itself: roles and grants, row-level security, and an IP allowlist. If end users need their own scoped access, Appwrite's docs suggest a backend that checks the user's Appwrite JWT and passes their identity on to your RLS policies. A direct connection to Nhost's database has the same gap, since Nhost's rules are enforced by its GraphQL API. Supabase is different here, because RLS runs inside Postgres and applies to every role that doesn't bypass it.

Three things that tripped me up in Appwrite's console:

- Row permissions don't show in the table view. To see who can read a record, you have to open that row's permissions panel, so scanning the table tells you nothing about who can see what.
- Row-level permissions have no Create, only Read, Update, Delete, because creating a row is controlled at the table level. Logical, briefly confusing.
- Custom permissions aren't checked against real users. The field takes `user:[USER_ID]`, `team:[TEAM_ID]/[ROLE]`, or `member:[MEMBERSHIP_ID]` as free text. I typed a user ID that doesn't exist and it saved without complaint. The Select users and Select teams pickers avoid this, but a typo in a typed role is a silently broken rule.

### Nhost: the rule is a form

In Nhost you can limit visitors to published posts without SQL and without per-row permissions. In the permissions editor (still labeled Preview in the dashboard) you pick the role and the action, then build the condition from three dropdowns:

```text
published   _eq   true
```

![Nhost's permission rule builder: published equals true, built from dropdowns.](/images/blog/supabase-vs-appwrite/nhost-rule-builder.png)

Underneath that's `{"published": {"_eq": true}}`, and the editor will show you either view. The rule that lets authors edit only their own posts looks the same, with the user's ID in place of a fixed value (the `X-Hasura` prefix is there because Nhost's GraphQL engine is Hasura):

```json
{"author_id": {"_eq": "X-Hasura-User-Id"}}
```

For updates, also leave `author_id` out of the columns authors can change, or preset it to the user's ID. Otherwise an author could reassign a post to someone else.

The playground has the same role switch the other two have. Set ROLE to `public`, run the query, and:

```json
{ "data": { "posts": [
    { "title": "Hello from Nhost", "published": true }
] } }
```

![Nhost's GraphQL playground as the public role: one row back, the draft hidden.](/images/blog/supabase-vs-appwrite/nhost-run-as-public.png)

One row came back out of two, and the draft stayed hidden.

The rule is stored as metadata next to your schema. If you work with the Nhost CLI, it's saved as files you commit with your migrations. Rules edited in the cloud dashboard, like mine, aren't versioned, and a later Git deployment can overwrite them.

Nhost applies the rule to every GraphQL request on that table: queries, subscriptions, and AI assistants acting for a user. You write it once and don't have to repeat it for each kind of request. Files get their own rules on the `storage.files` table, built in the same editor. A direct database connection skips all of this, since it never goes through the GraphQL engine.

By default, access is denied. No role except `admin` can read anything until you grant it, so a table you forget to set permissions on stays private, the same as on Appwrite, and on Supabase for tables made in its Table Editor. The catch is the error message: for a role without access, the table simply isn't in the schema, so you get `field 'posts' not found in type: 'query_root'` instead of anything that mentions permissions.

![Nhost's permissions matrix: roles down the side, actions across the top.](/images/blog/supabase-vs-appwrite/nhost-permissions-matrix.png)

### Which permission model fits

The real difference is what a rule can check and how you write it. Supabase rules are SQL, so they can check anything SQL can. The dashboard has templates and an AI assistant to start you off, but what you end up with is SQL your team has to read and maintain. Appwrite checks who the user is against grants stored on the table and on each row. That's easy for the whole team to read, but when access depends on what's in the row, your code has to rewrite that row's grants every time the data changes. Nhost checks both the user and the row, and you build the rule in a form. If a rule gets too complex for the form, you can still write that part in SQL.

Think of the hardest access rule in your app. If your permission system can't express it, you'll end up writing that check somewhere worse: in the client, in a wrapper endpoint, or on every row by hand.

## Storage

Each platform protects files the same way it protects your data. I didn't test file permissions myself, so this section comes from each platform's docs.

Supabase keeps a record of every file in a Postgres table and protects it with RLS policies, like any other table. If you can write a policy for a row, you can write one for a file. It also works with standard S3 tools, so you can manage files from the AWS CLI.

Appwrite gives each bucket, and each file once you turn on file security, its own permissions, using the same roles as tables. That brings the same limit as with tables: a rule can check who the user is, but not anything about the file or the data it belongs to. Appwrite also [added an S3-compatible API](https://appwrite.io/blog/post/announcing-s3-api) in September, so S3 tools like the AWS CLI work there too, signed with a project API key.

In Nhost, files get their own permission rules on the `storage.files` table, built in the same editor and with the same kind of conditions as your tables, and the storage API checks them on every upload and download. (Presigned URLs are on by default for every bucket. They're checked once, when they're created, and after that anyone with the link can download the file until it expires, 30 seconds later by default.) File records live in Postgres, so a file rule can follow a relationship to the row the file belongs to. Nhost can also resize images and convert them to WebP or AVIF on download, and that's included on the free plan, while Supabase and Appwrite only transform images on paid plans. What Nhost doesn't have is an S3-compatible API: files go through its own HTTP API and SDK.

Most apps have public files (like avatars, product images) and private ones (invoices or user uploads). When you test a platform, upload one of each and see who can open it.

## Functions, and the runtime arms race

| Capability | Supabase | Appwrite | Nhost |
| --- | --- | --- | --- |
| Runtime | Deno 2.1, all regions | Node, Bun 1.4, Deno, Python, PHP, Ruby, Rust, and more | Node.js (JavaScript/TypeScript), plus any container via Run on paid plans |
| Deploy | CLI, dashboard, Management API, GitHub integration | CLI, console, Git triggers | GitHub integration (the CLI can deploy a pushed commit, or a Run image) |
| Language freedom | JavaScript/TypeScript, plus WebAssembly | Wide | Narrow in Functions, any language in Run (paid plans) |

Appwrite supports the most runtimes of the three, from Node and Python to Rust, and it [recently added Bun 1.4](https://appwrite.io/blog/post/announcing-bun-1-4-runtime).

Supabase gives you one runtime, which means one set of behaviors to learn. For webhooks and glue code, that's plenty. If your pipeline has a Python ML step, it has to run somewhere else, and the same is true of Nhost on the free plan. Supabase [announced Compute](https://supabase.com/blog/select-2026-build-anything) for other languages on October 2nd, but it's a private alpha with a waitlist.

The runtime itself is worth watching too. Supabase Edge Functions run on Deno, and on October 9th Deno [announced it's joining Cloudflare](https://deno.com/blog/cloudflare), with bug-fix and security releases of the runtime promised for another year. On October 12th, Supabase [said](https://x.com/supabase/status/2109630227085168640) that Edge Functions run on its own infrastructure, not on Deno's hosted services, and that existing functions stay supported. It plans a migration path to Compute, which will run Deno, Node.js and Bun, and aims to have it ready well before Deno's support ends. It hasn't shared a timeline yet.

Nhost splits this into two products. Functions run JavaScript/TypeScript on Node.js and handle HTTP endpoints, event triggers, cron triggers and one-off scheduled events. For anything else there's Nhost Run, on Pro and Team plans, which deploys any Docker container next to your stack: Go, Python, Rust, or anything that builds into an image. You pay for the vCPU and memory you allocate. I couldn't try it on the free plan.

## Realtime

Supabase Realtime streams database changes over WebSockets, and each subscriber only gets the rows its RLS policies let it read (deletes are the exception). Broadcast sends messages between clients, and [since June 2026 it also supports binary payloads](https://supabase.com/changelog/46834-realtime-broadcast-now-supports-binary-payloads), which cuts JSON overhead if you're pushing sensor data or image frames. Presence tracks who's online in a channel. Private channels use RLS policies to decide who can join. The dashboard also lets you size Realtime's database connection pools and cap concurrent clients, up to your plan's limit (200 on Free).

Appwrite realtime uses the same permissions as your data, so a client subscribed to a table only sees rows it's allowed to see. It also has a [Presences API](https://appwrite.io/blog/post/announcing-presences-api) for online, typing and activity states. It launched on Cloud in May and came to self-hosted in [version 1.9.5](https://github.com/appwrite/appwrite/releases/tag/1.9.5). Appwrite's native Postgres has no realtime at all.

Nhost does realtime with GraphQL subscriptions. Take any query, change `query` to `subscription`, and you get a live stream over a WebSocket. The same permission rules apply, so a subscribed client only gets the rows its role is allowed to see. Under the hood these are live queries that re-run about once a second, so they're simple but not instant. There's no broadcast or presence feature, so to show who's online you'd keep statuses in a table and subscribe to it.

## Where the AI lives

While building the test app, I ran into AI features in the Supabase and Appwrite dashboards. Nhost's AI service and Nhost Run need a Pro plan, so I couldn't try them on the free plan I used for everything else. What follows about AI for your users, on all three platforms, comes from the vendors' docs, not from my test.

Supabase and Appwrite both have AI help in the dashboard, free tier included. Supabase's assistant is a panel you can open from any page. It writes SQL and RLS policies, with starter prompts like "Set up RLS policies" and "Generate sample data", and the Policies page links straight to it. Appwrite uses AI to get you started: when you create a table, it suggests columns and indexes from the table name. It can also fill the new table with sample data, though that part is generated from your column types, not by AI.

Both help you, the developer, while you build. For AI your users touch, both give you building blocks rather than a finished feature. Supabase has pgvector, an embedding model that runs inside Edge Functions, and an OAuth 2.1 server (beta) that agents can sign in through. On October 2nd it also announced an [MCP server block](https://supabase.com/blog/select-2026-build-anything) for your own app. It's an Edge Function you add to your project, and it runs each agent call as the signed-in user, under your RLS policies. Appwrite's [VectorsDB](https://appwrite.io/blog/post/announcing-vectorsdb) (beta) can generate embeddings with a built-in model, though a VectorsDB database needs a paid plan. Its OAuth2 server lets you [build an MCP server](https://appwrite.io/blog/post/turn-your-app-into-an-mcp-server) that acts as the signed-in user. On both, you write the agent's tools yourself.

Nhost packages more of this as ready-made services. Its AI service, [Graphite](https://docs.nhost.io/products/ai/), is a Pro and Team add-on that uses your own OpenAI key, and it comes in two parts:

- **Auto-Embeddings** keeps an embeddings column up to date. Every few minutes it picks up new or changed rows through a query you write, gets their embeddings from OpenAI, and adds GraphQL queries for natural-language and similarity search. The embeddings live in Postgres with pgvector, so you can also query them yourself.
- **AI Assistants** let your users chat with your data. You give each assistant a set of tools (GraphQL queries, mutations or webhooks), and the model asks Graphite to run them with the user's session, so it never touches the database itself. Different assistants can see different parts of your data, and you decide which users can use which assistant.

There's also a [Backend MCP Server](https://docs.nhost.io/products/ai/mcp/), a small open-source service you deploy next to your project (on Nhost Cloud that means Nhost Run, which needs a paid plan). It gives MCP clients like Claude every query and mutation in your GraphQL API, with no tools to write one by one. Users sign in through Nhost Auth, so the agent works with their account and their permissions.

Searches, assistant queries and MCP calls run with the signed-in user's token, so the AI only gets back rows that user is allowed to see. Webhook tools get the user's headers but have to check access themselves, and embeddings are generated in the background with admin access, which sends the embedded text to OpenAI.

## Where Nhost falls short

Since I work at Nhost, here's what I'd want spelled out if I were reading this:

- The AI service and Nhost Run need a paid plan, and so does hosting the MCP server on Nhost. Graphite is billed as an add-on and uses your own OpenAI key.
- Functions only run JavaScript and TypeScript on Node.js, and on the free plan they time out after 10 seconds.
- Realtime is live queries that re-run about once a second. There's no broadcast or presence.
- Storage has no S3-compatible API.
- Sign-in works with a built-in list of providers. You can't plug in any OIDC provider the way you can on Supabase and Appwrite.
- Access rules live in the GraphQL layer, not in Postgres, so a direct database connection skips them.
- The community is much smaller than Supabase's or Appwrite's, so there are fewer tutorials, integrations and answers to lean on.

## So which one

I know it's a cliché, but there's no single answer to which one is best. I built one small app on free plans, and a full picture would take running a real production app on each. But it did show the differences you hit on day one: how you link tables, how you write access rules, and what your API looks like.

**Supabase** is for you if you open a SQL editor before you open the docs. Your app's hard part is the data: reports, joins, analytics, logic you'd happily write in Postgres. Supabase lets you keep all of that in the database, access rules included. Nhost gives you the same Postgres, so between those two it comes down to the API and the rules. Do you want REST or GraphQL? And would you rather write rules as SQL policies that Postgres enforces itself, or build them in a form and have the GraphQL API enforce them? Either way, someone on the team has to own them.

**Appwrite** is for you if you're building a mobile app or a frontend-heavy product and would rather never think about the database. Each user owns their own data, maybe shares it with a team. That's the shape Appwrite fits best, with login, files, push notifications and hosting all in one console.

**Nhost** is for you if you want a GraphQL API over Postgres, with access rules you build per role in a form. It's also built for AI agents working inside your app on your users' behalf, through an MCP client like Claude or an assistant you build into the app. All three platforms can now sign an agent in as a user and apply that user's rules. Nhost's difference is how much comes ready-made: its MCP server gives agents your GraphQL queries and mutations without you writing any tools, and Graphite adds managed search and assistants under the same rules. On Nhost Cloud both need a paid plan, so they weren't part of my free-tier test.

None of these are bad choices, and I got the same small app working on all three. The one that fits is usually the one whose defaults match how you already think about your data, which is easier to feel than to read about. So if you're torn between two of them, build the same small thing on both. That's where this whole post came from.

If Nhost sounds like your fit, the free plan is enough to run the same data and permissions test yourself. To try the AI service or host the MCP server on Nhost, you'll need a Pro plan.
