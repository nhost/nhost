I'm still poking at how backend platforms hold up when someone builds on them with AI. Last time it was five prompt-to-app builders. This time I wanted to try a different combination: Claude Code and the CLIs of three popular backend platforms.

Each platform got two apps to build. The first is the same one I built with prompt builders in another post. The second is a bit harder: it needs more of the backend, and more of Claude's time.

This is not a benchmark and it isn't a full comparison of the platforms. These are small apps and one run each. What I set out to do was give the three an equal start (speaking of equality, that took a lot more manual cleanup between runs than I expected), watch what happened, and pass on the results with a few thoughts of my own. Both prompts are below in full, so you can run them yourself.

## The same starting line for everyone

Same conditions for both apps and all three platforms.

- Claude Code running Opus 5.5 on medium reasoning throughout
- An empty folder and a brand new session for every run
- An empty cloud project for every run
- Everything against the cloud, no local stacks and no Docker anywhere
- Email confirmation switched off on all three, so test accounts could sign in straight away
- No plugins, skills or notes from earlier work anywhere the agent could reach, so whatever it knew about a platform came from training and not from my machine

Neither prompt mentions permissions, roles or backends. So the first thing I watched for is where each platform leads an agent to put the access rules when nobody tells it to. I also wanted to know how smoothly the agent would get along with each platform, how often I'd have to step in, and how long the whole thing would take.

## First app: a poll with a secret ballot

The first line of the prompt named the platform and the project. Everything after it was identical, word for word, in all three:

> Build a polling app.
>
> Users sign up and log in with email and password. Different users log in from different browsers and share the same data.
>
> Anyone logged in can create a poll with a question and a few options, and can vote once per poll.
>
> Everyone sees the total votes for each option. Each user sees which option they voted for. Nobody can find out how another specific user voted.
>
> Only the person who created a poll can delete it.
>
> Keep it minimal, styling does not matter.

I expected "nobody can find out how another specific user voted" to be the challenging part. If people can read the votes to count them, they can also see who cast each one. So the votes have to be closed, and the totals have to come from somewhere else.

## What happened

**All three produced a working app with the access rules enforced in the data.**

|  | Nhost | Supabase | Appwrite |
| --- | --- | --- | --- |
| Time | 2:46 | 3:11 | 4:43 |
| Cost | $0.56 | $0.70 | $1.00 |
| Context read | 705K | 1.3M | 1.7M |
| Mistakes it had to fix | 1 | 3 | 3 |
| Times it stopped to ask me something | 0 | 0 | 0 |
| Docs pages opened | 0 | 0 | 0 |
| Where the rules ended up | row rules in the database | row-level policies in the database | database closed, everything through a server function |
| What it handed back | a local page | a local page | a deployed site on a public URL |

Appwrite's time stands out, but there's a reason for it. It wrote a server function and put the finished app online on a public URL. I never asked for either, and the other two didn't do it. My guess is that Appwrite's own hosting makes deploying the obvious next step, so the agent just took it.

## Nhost: fastest, but with an extra step before the start

2 minutes 46 seconds. It created three tables and a view, set the permissions, wrote the page, then ran its own two-user test against the live project and reported each rule as passing.

Votes are readable only by the person who cast them. The rule in the dashboard reads `user_id _eq X-Hasura-User-Id` on the `user` role, and the `public` and `anonymous` roles have no access to the table at all. Update and delete are closed too, so a vote cannot be changed once cast.

![Nhost: the select rule on the votes table](/images/blog/supabase-vs-appwrite-vs-nhost-cli-claude-code/nhost-votes-permissions.png)

The totals come from a separate view, `poll_option_totals`, which counts rows without exposing them. It got there in under three minutes, without being told.

One mistake, and it was in its own test script rather than the app: single quotes in a GraphQL query, which GraphQL does not accept. It noticed, fixed it, and the check passed. The schema and permissions worked on the first attempt.

One thing had to happen before the clock started: a Nhost admin secret can't be read anywhere, in the dashboard or through the CLI, so I overwrote it with one of my own and handed it to the agent in the prompt. On Supabase and Appwrite it got there by itself, from a CLI login I had already done.

## Supabase: let itself in, then took three wrong turns

3 minutes 11 seconds, start to finish, without asking me anything. It got its own access, installed the schema, tested with two throwaway users and deleted them afterwards.

Row-level security is on for all three tables, with policies written only for the `authenticated` role: `cast own vote` on insert and `read own votes` on select for the votes table, `read polls` and `creator deletes poll` for polls, `read options` for options. Nothing for anonymous visitors.

![Supabase: the policies on the polling app](/images/blog/supabase-vs-appwrite-vs-nhost-cli-claude-code/supabase-poll-policies.png)

The three mistakes are worth reading as a group, because two of them are about error messages rather than code.

1. It combined two CLI flags the tool refuses together. The error named the fix and the next attempt worked.
2. The admin key it saved was truncated. The CLI hides most of a secret key unless you pass a reveal flag, and gives no warning that what you got is a fragment. Its test users were never created, the first failure came back as `permission denied for function create_poll`, and it spent two debugging steps chasing a permissions bug that was actually a failed login.
3. One it avoided rather than made: loading data from inside the login-change handler can freeze the Supabase client, so it deliberately delayed that call. It only mentioned this when asked afterwards.

Notably, the project was created with the security settings left at their defaults: automatic row-level security on new tables was not enabled. The agent turned RLS on itself.

## Appwrite: the slowest, with the database closed

4 minutes 43 seconds and a dollar. It also built something the other two did not.

The votes table has no table-level permissions at all. The Security tab is empty: no role has been granted anything, and row-level security is on. No client can read or write that table directly, under any identity. Every write goes through a single server function that checks who is asking.

![Appwrite: no table permissions on votes, row security on](/images/blog/supabase-vs-appwrite-vs-nhost-cli-claude-code/appwrite-votes-permissions.png)

This is stricter than either of the others, where a signed-in client does talk to the database and a rule limits what comes back. Here the client never reaches the data.

The agent explained why afterwards, and the reason is a property of the platform rather than a preference: client-side permissions in Appwrite cannot stop someone writing a row with another person's ID in it. The platform does not check that the ID in the record belongs to whoever created it. Preventing forged votes meant moving every write to the server.

That single design decision accounts for most of the extra time and cost.

Three mistakes. It typed `appwrite projects` where the command is `project`. Its first check of the SDK version failed. And after deploying, it took the first URL the tool printed, which turned out to be a private preview link that sends visitors to an Appwrite sign-in page. It had to create a public domain separately. Its own words: a real user would have hit a login wall.

One side effect worth recording. Appwrite normally needs a web platform registered for a given hostname before a browser is allowed to talk to it. The agent sidestepped that entirely by deploying to Appwrite's own hosting, where no registration is needed.

## Three answers to the same question

One requirement, three architectures, all correct.

**Nhost** closed the votes table to everyone but the row's owner and added a view that returns counts without the rows behind them.

**Supabase** wrote a policy letting each user read their own votes, and a function running with extra privileges to return the totals.

**Appwrite** closed the table to every client and routed all reads and writes through one server function.

The shape is the same in all three: votes locked to their owner, totals served by something that can see more than the caller can. What differs is where that something lives, and each platform pushed the agent to its own answer without being asked.

## A harder second app

The polling app is small, and the obvious objection to everything above is that a task that size cannot separate three mature platforms. So the same three got a second job, on fresh projects, harder in the places that matter.

> Build a team incident logger.
>
> Users sign up and log in with email and password.
>
> Anyone logged in can create a team and invite other users to it by email address. A user can belong to several teams.
>
> Incidents belong to a team. Anyone on that team can report one with a title, a description, and a severity of low, medium, high or critical, and can attach a .txt log file to it.
>
> People on a team can see that team's incidents and open their attachments. People outside the team cannot see either, including the attached files.
>
> Only the person who reported an incident can edit it, delete it, or mark it resolved.
>
> When an incident is reported as critical, the platform itself should react to that and run a server function that records an alert was sent.
>
> Keep it minimal, styling does not matter.

Four things here did not exist in the first task.

**File storage**, and with it permissions on files rather than rows. This is the classic leak: the record is locked down and the file sits on a URL anyone can open.

**Access by membership** instead of by ownership. In the polling app the rule was "is this row mine". Here it is "am I on the team this incident belongs to", which means following a relationship to a third table.

**A server function**, deployed by the agent rather than written into the page.

**The platform reacting on its own.** The function has to run because the data changed, not because the app called it. Each platform has a different mechanism for that, and none of them came up in the first task.

The question that matters most here: can someone outside a team open another team's attachment from a direct link?

### What happened

|  | Supabase | Appwrite | Nhost |
| --- | --- | --- | --- |
| Time | 4:48 | 6:22 | 8:20 |
| Cost | $1.25 | $2.21 | $2.64 |
| Context read | 1.0M | 3.3M | 5.0M |
| Mistakes it had to fix | 2 | 2 | 1 |
| Times it stopped to ask me something | 0 | 0 | 0 |
| Docs pages opened | 0 | 0 | several |
| Its own end-to-end checks | 30 | 20 | 31 |
| Where the file rule ended up | a policy on the storage path | row permissions granted to a team | a relationship chain in the database |
| What it handed back | a local page | a deployed site on a public URL | a local page |

The order flipped. On the polling app Nhost was the quickest and cheapest and Appwrite the slowest; here it's the other way round, with Supabase ahead and Appwrite between the two.

The row that tracks everything else is context read: 1M, 3.3M, 5M. Time and cost follow it in the same order. The more an agent has to read and re-read to find its way around a platform, the longer the job takes and the more it costs.

All three got the access rules right again, and all three did it differently. I read the permissions in the projects themselves rather than going by what the agents told me, so the code below is what's actually deployed.

## Supabase on the incident logger

### Nothing to ask me for

The cheapest and quickest of the three, and it needed nothing from me. It got its own project access from an existing CLI login, applied the migration, deployed the Edge Function straight from the CLI, and was finished before I'd read the first half of its output.

It tested its permission rules inside a transaction it forced to roll back, so none of its test data was ever written. Then it ran Supabase's own security advisor unprompted and fixed two of its findings: a trigger function that was callable over RPC, and a missing fixed `search_path`.

It signed off by warning me about email confirmation, which the project has on by default and I had already switched off. It never checked the project's auth settings, and nothing in the platform pushed it to.

### Eight policies and a folder name

Eight row-level policies across five tables, all scoped to the `authenticated` role. Read-if-member on everything, insert for members, update and delete for the reporter only. `teams` and `team_invites` have no write policies at all, because creating a team and inviting someone go through functions running with elevated privileges instead.

Files are the interesting part. Each attachment is stored in a folder named after the team, and the read policy checks the path:

```sql
bucket_id = 'incident-logs'
AND is_team_member(try_uuid(storage.foldername(name)[1]))
```

Upload and delete are restricted to the reporter. Critical incidents are handled by a database trigger calling the Edge Function through `pg_net`, with the shared secret held in Vault.

## Appwrite on the incident logger

### The only one that shipped it

Like last time, it put the app online, which nobody asked for. Appwrite hosts sites itself, so the agent had somewhere obvious to deploy to and did. It cost it a detour: a browser won't talk to an Appwrite project until the site's domain is registered as a web platform, and it hit an error setting that up.

Its `setup.sh` is a record of the commands it ran rather than something that works from scratch: the first attempt failed partway because optional columns need an explicit flag.

It tested that an outsider can't list incidents, open one by id, view or download a file, or post into a team. It didn't click through the finished app, on the grounds that doing so would create a real account on a live public site.

### Teams it didn't have to build

Appwrite didn't build teams at all. It used the platform's own Teams feature, which already has invitations, membership and email delivery — the only one of the three that didn't model this by hand.

Access is granted per row to a team, and the incidents table grants All users nothing but `create`. That matters: Appwrite combines table and row permissions with OR, so any read granted at the table level would silently cancel the row-level privacy. Appwrite also refuses to let a user grant access to a team they aren't in, which closes a whole class of mistake before it can happen.

That choice had a price. Only the team's creator can invite, because that is Appwrite's default for team owners. Letting every member invite would have needed a server function. The agent flagged this itself as a decision I might want changed.

The alert function is attached to Appwrite's own database events, so the platform invokes it on create and update with no glue in between.

## Nhost on the incident logger

### Two thirds of it was plumbing

Nhost was the slowest here, and by the agent's own breakdown most of the run went on getting the code into the project. Deployment, working out the platform and rebuilding metadata took roughly two thirds of it between them.

There is no CLI command that applies migrations and metadata to a cloud project, so the agent pushed schema and metadata through Hasura's HTTP API, created the migration-tracking table by hand, and inserted a row so the later deploy wouldn't run the same migration twice. It also found that `nhost init` leaves the metadata folder empty while a deploy applies whatever is in it, so it wrote out metadata for every table including the built-in auth and storage ones, to avoid wiping them. Functions deploy only from a connected GitHub repo, so the alert function sat untested until a full push-and-deploy cycle near the end.

It also did something none of the others did: it found a real hole in its own implementation and fixed it mid-run. Its invite trigger ran before Hasura's permission check, so someone outside a team could use invites to probe whether an email address had an account. It added a membership check and reran its suite.

### The tightest rules of the three

Five tables and the tightest permission set of the three, once you read the deployed metadata rather than the summary.

Reading a file is allowed if you uploaded it, or if the file walks three relationships out to a team you belong to:

```yaml
_or:
- uploaded_by_user_id: {_eq: X-Hasura-User-Id}
- incidents: {team: {members: {user_id: {_eq: X-Hasura-User-Id}}}}
```

Uploads are restricted by bucket, by filename and by mime type, so a binary renamed to `.txt` is refused on the type rather than the name. The uploader's id is stamped from the token and can't be set by the client. Editing an incident is restricted to its reporter, and a separate check stops anyone attaching a file they didn't upload themselves.

Critical incidents fire a Hasura event trigger on insert, and on update only when the severity column changes, with three retries and a shared secret in the header.

![Nhost: reading a file walks three relationships out to the team](/images/blog/supabase-vs-appwrite-vs-nhost-cli-claude-code/nhost-file-permissions.png)

## I checked the files myself

This is the one thing I didn't want to take anyone's word for. On each platform I made an account, created a team, reported an incident with a `.txt` attached, and then tried to reach that file from three places: signed out, signed in as someone who isn't on the team, and signed in as a team member.

**All three held.** Only the team member got the file.

What differed was how they said no, and what there was to say no to.

Appwrite is the only one where the attachment has a URL you could paste into a chat. The session travels in a cookie, so the same link behaves differently depending on who opens it: a file for a team member, a 404 for everyone else.

Supabase and Nhost never hand you a link at all. The file comes down through the SDK with a token attached, which means there's nothing to copy and forward in the first place. Hitting the storage endpoint directly returns an error no matter who you are, because the browser doesn't send that token when you type a URL into the address bar.

The error messages are worth a look side by side:

|  | Anonymous request to the file |
| --- | --- |
| Appwrite | `The requested file could not be found` |
| Supabase | `Bucket not found` |
| Nhost | `you are not authorized` |

Two of them pretend the thing doesn't exist. Nhost tells you it exists and you can't have it. Appwrite's agent had flagged exactly this behaviour as a debugging annoyance when I asked it about pitfalls, and here it is.

## One docs visit in six builds

Across six runs on three platforms, **five of them opened zero documentation pages.**

What they read instead was the CLI's `--help` output and the type definitions inside the installed SDK. On Supabase that help text was what revealed the `--reveal` flag the agent was missing, and later the `--use-api` flag that let it deploy a function without Deno installed. On Appwrite it was `--help`, `npm view` for SDK versions, and the error messages themselves.

The single exception was Nhost on the harder app, where the agent opened the docs on functions, event triggers and storage permissions before writing anything. So those parts weren't in its memory.

## The same trap, three times over

Asked afterwards what was easy to get wrong about permissions on their platform, all three came back with the same answer: showing vote totals without revealing who voted for what.

The Nhost agent explained it best. Permissions there work row by row, so letting everyone read the votes table to count votes also lets them read who cast each one. Its fix was a separate view. Its comment: you have to come up with that yourself, it is not the obvious first move.

Supabase needed a function running with elevated privileges, and its agent warned that writing that function carelessly leaks exactly what you were protecting. Appwrite's agent pointed out that table and row permissions are combined with OR, so unless the table grants no read at all, row-level privacy silently does nothing.

## What they knew was wrong with their own work

I also asked each one where its own work was most likely to be broken in a way its tests wouldn't catch. All three came back with long lists.

The worst was Supabase's. Invites there are applied the moment the user row is created, which is before the email address has been confirmed. That's fine as long as confirmation is on, since an unconfirmed account can't log in. But this is the same agent that had suggested turning confirmation off to make testing easier. Do that, and anyone who guesses an invited address can sign up with it and land inside that team, incidents and files included. The agent's own line: until that's fixed, don't turn confirmation off.

Nhost's agent ran into a smaller version of the same thing, except it spotted it while building. Its invite trigger ran before the permission check, so someone outside a team could use invites to test whether an address had an account. It added a membership check and reran its tests. Supabase's build has the same hole, and its agent mentioned it only when I asked.

Other things they volunteered, none of which their test suites covered:

- **"Only `.txt`" is weaker than it sounds on all three.** Supabase and Appwrite check the file extension and the content type the browser declares. Nhost checks the mime type recorded at upload. None of them looks at what is actually in the file.
- **Alerts can vanish silently.** Supabase's `pg_net` call fires once with no retry; if the function is down, nothing is recorded and nothing says so. Nhost retries three times and then gives up just as quietly.
- **Orphaned files.** On Supabase and Appwrite, a failure between uploading a file and saving the incident leaves the file in storage with nothing pointing at it, and in one case nobody able to delete it.
- **Membership changes.** On all three, someone removed from a team keeps edit rights on incidents they reported. None of them built a way to remove a member, so it doesn't come up yet.
- **Weak assertions in their own tests.** Appwrite's agent admitted that any 404 counted as "access denied" in its suite, so a typo in an ID would have passed too, and that its "no alert for a low-severity incident" check simply waited six seconds.

## What the rules cost

Asked what the per-file permission check costs as data grows, the three answered at very different levels of honesty about their own work.

Supabase's agent was the most specific and the most self-critical. Opening one file is two indexed lookups. Listing them is where it degrades: the membership check is a function Postgres can't fold into the query, so it runs once per row, and `try_uuid` opens a mini-transaction on every call. It offered a cheaper pattern the planner could evaluate once per query, then said plainly that it had run no `EXPLAIN`, no load test and no volume test.

Appwrite's agent noted that each team a user joins lengthens the list of roles checked on every query, that the app stops at a hundred incidents with no paging beyond that, and that viewing an attachment costs an extra rate-limited request. It added an index and measured nothing.

Nhost's agent added indexes on the columns its relationship chain walks, and said it couldn't measure anything without direct database access.

## What I took away from this

After the prompt-builder test I didn't really doubt the backends would handle either of these. They did. There are rough edges in how you get there, but I'd expect platforms to get friendlier to agents over time, and agents to learn the platforms better.

Which is probably why Claude Code came out so differently on each one. Most of it comes down to how well it already knows what's under the hood, and that will shift depending on the task you give it.

One visit to the docs across six builds still surprises me. Everything else came from the CLI's help text, the SDK's types, and whatever the model already knew. If that's how people are building now, then help output and type definitions are doing work most teams think their documentation site is doing.

The other thing I noticed is that none of these agents told me when something was risky. They told me when I asked. All three had a list ready about where their own work might be wrong, and none of it came up until the question did.

Both of these are still small apps, of course. What happens on something real, with a schema that keeps changing and features piling up, is another question. That's the next test.
