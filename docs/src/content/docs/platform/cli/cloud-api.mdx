`nhost api` sends GraphQL requests from the CLI to the Nhost Cloud API with your account's permissions. The Nhost Cloud API manages your organizations and projects, and is separate from your project's own [GraphQL API](/products/graphql). The command has two subcommands: `nhost api schema` prints the schema, and `nhost api query` sends a query or mutation. For the full syntax, see the [command reference](/reference/cli/commands#api).

If your agent has the [CLI MCP tools](/platform/cli/mcp) and they cover your task, use them instead. Use `nhost api` for tasks they don't cover, or when the MCP server isn't set up, such as in a script.

The MCP server allows mutations to Nhost Cloud only if `enable_mutations` is on in its [configuration](/platform/cli/mcp/configuration). With `nhost api`, your agent can add `--allow-mutations` to any call, so set it to ask before it runs `nhost api query` (see [Set up your agent](#set-up-your-agent)).

The Nhost Cloud API calls projects `apps`, so that's the name you see in the schema and in the examples on this page.

## Sign in

`nhost api` uses your CLI login session. If you haven't signed in yet, run:

```bash
nhost login
```

This opens your browser to sign in to your Nhost account and saves the session in `~/.nhost/state/auth.json`, or in `$XDG_STATE_HOME/nhost/auth.json` if `XDG_STATE_HOME` is set. Other CLI commands and the CLI MCP server use the same session.

`nhost api` never opens a browser or asks for input. Each call gets a short-lived access token from the saved session and saves the session back to the file when it's renewed. If there's no session, or it has expired or been revoked, the command fails, and you need to run `nhost login` again.

To use a personal access token instead, for example in CI, set the `NHOST_PAT` environment variable. When it's set, `nhost api` uses the token and ignores the saved session. You can create a token in the dashboard under **Account Settings**.

## Set up your agent

In your agent's command permissions:

- Let `nhost api schema` run without approval. It takes no arguments, so allow only that exact command rather than a prefix.
- Require your approval for every `nhost api query` call. Reads can return sensitive values, such as a project's secrets and its Hasura admin secret, and your agent sees everything the command prints. Calls with `--allow-mutations` can change your organizations and projects.

If your agent runs in a sandbox and uses your login session, give it read and write access to the session file. Without write access, a renewed session isn't saved, and a later call can fail until you run `nhost login` again. With `NHOST_PAT` set, the session file isn't used.

:::caution
When a call includes `--allow-mutations`, the CLI sends the mutation as written, with no further checks or confirmation. Review the operation and variables before you approve the call.
:::

## Inspect the schema

`nhost api schema` prints the introspection result (`{"__schema": ...}`) as JSON. Save it to a file rather than printing it into an agent's context, and inspect it with `jq`. For example, to see the arguments the `updateApp` mutation accepts:

```bash
nhost api schema > cloud-schema.json
jq '.__schema.mutationType.fields[] | select(.name == "updateApp")' cloud-schema.json
```

## Send a query

`nhost api query` takes one quoted GraphQL document and an optional `--variables` JSON object. It refuses mutations unless you pass `--allow-mutations`, and always refuses subscriptions.

For example, to list up to five projects, ordered by name:

```bash
nhost api query 'query {
  apps(limit: 5, order_by: {name: asc}) {
    id
    name
  }
}'
```

The output looks like this:

```json
{"apps":[{"id":"<project-id>","name":"My project"}]}
```

## Send a mutation

This example renames a project. Replace `<project-id>` with an `id` from the previous query, and `New project name` with the new name:

```bash
nhost api query --allow-mutations 'mutation RenameProject($id: uuid!, $name: String!) {
  updateApp(pk_columns: {id: $id}, _set: {name: $name}) {
    id
    name
  }
}' --variables '{"id":"<project-id>","name":"New project name"}'
```

`nhost api` doesn't retry the GraphQL request. After a network error, you can't tell whether the mutation was applied, so query the current state before you send it again.

## Output and errors

On success, `nhost api schema` and `nhost api query` print only the response's `data` field as JSON to stdout. On any failure, the command exits with code `1` and writes the error to stderr. For GraphQL and HTTP errors, the error includes the server's response.
