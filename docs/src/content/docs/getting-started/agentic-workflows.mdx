Nhost speaks the [Model Context Protocol](https://modelcontextprotocol.io/), so an AI assistant can read your schema, run queries, and write migrations and permission rules directly.

## Connect your assistant

Hand the onboarding file to your assistant and it does the whole setup:

<Tabs syncKey="assistant">
<TabItem label="Claude Code">
```sh
curl -fsSL https://docs.nhost.io/install-mcp | claude
```
</TabItem>
<TabItem label="Codex CLI">
```sh
curl -fsSL https://docs.nhost.io/install-mcp | codex exec -
```
</TabItem>
<TabItem label="Gemini CLI">
```sh
curl -fsSL https://docs.nhost.io/install-mcp | gemini
```
</TabItem>
<TabItem label="Other">
```sh
curl -fsSL https://docs.nhost.io/install-mcp | <your-assistant-cli>
```
</TabItem>
</Tabs>

It asks whether the project is local or on Nhost Cloud, then configures that one. A local project needs to be running first: see [the CLI quickstart](/getting-started/local-development/cli) if you don't have one.

Then ask for what you want, for example:

<Prompt copy="Add a published_at column to posts, allow the user role to read only published rows, and show me the migration before applying it.">
Add a `published_at` column to `posts`, allow the `user` role to read only published rows, and show me the migration before applying it.
</Prompt>

### Or connect without installing anything

Nhost hosts a read-only MCP server at <CopyText text="https://mcp.nhost.io" /> that answers questions about your organizations, projects, and deployments.

<Steps>

1. In your client, add a custom connector or remote MCP server with that URL.
2. Authorize the request on the Nhost consent page.
3. Ask the assistant about your projects.

</Steps>

It cannot change configuration or touch your project's data. See [Hosted MCP server](/platform/cloud/hosted-mcp-server).

## Keep it in bounds

An assistant acts with whatever credentials you hand it.

- **Full access locally, least access everywhere else.** Start a cloud project at `allow_mutations = []` and widen deliberately.
- **Admin secrets stay on local projects.** They bypass permissions entirely. Use a [PAT](/platform/cli/mcp/cloud-setup#authenticate) against real data so your permission rules still apply.
- **Read what it writes.** Migrations and permission rules are code.

[Scoping access](/platform/cli/mcp/cloud-setup#scoping-access) covers the rest, including why `manage_metadata` is broader than it looks.

## Which server am I using?

| | CLI MCP server | Hosted MCP server |
|---|---|---|
| **What it is** | Part of the Nhost CLI | [Backend MCP](/products/ai/mcp), run by Nhost |
| **Points at** | One project, local or on Nhost Cloud | Your orgs, projects, deployments |
| **Runs** | On your machine | On Nhost's servers |
| **Setup** | Install the CLI | Nothing to install |

Both of these are for *you*. [Backend MCP](/products/ai/mcp) is the service behind the hosted one, and it is also what you deploy in front of your own project to give your **application's users** an AI interface. Same service, your backend.
