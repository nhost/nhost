Give it full access on a local project. Nothing there is real, and the faster loop is worth more than the guardrails. Against a project on Nhost Cloud, start read-only and widen deliberately.

## 2. Check 3 things yourself

The assistant does the work. These are the parts worth your own eyes.

**Read the migration.** Every schema change writes a file under `nhost/migrations/`. That file runs against every other environment, so reading it is the fastest way to catch a column type or a nullability choice you did not intend.

**Verify permissions.** They are the security boundary for your project: every GraphQL request runs under a role and is filtered by these rules, including the assistant's own. Open **Database → Permissions** in the dashboard and read back what was applied. See [Permissions](/products/graphql/permissions).

**Set secrets yourself.** Ask which variables a service needs, then enter the values through the dashboard so the real credential never passes through a chat transcript. See [secrets](/platform/cloud/secrets).

## 3. Commit what it wrote

This is what makes the workflow durable rather than a pile of untracked changes. The assistant writes migrations under `nhost/migrations/`, metadata under `nhost/metadata/`, and configuration in `nhost.toml`. Commit them, and the project becomes reproducible: another developer runs `nhost up` and gets the same backend, and [deployments](/platform/cloud/deployments) apply the same migrations to Nhost Cloud.
