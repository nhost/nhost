You do not have to learn the Nhost CLI to build on Nhost. Connect an AI assistant to your project and describe what you want instead. The assistant runs the commands, applies the change, and writes the migration files; you review what it wrote and commit it.

This works the same way whether your backend runs on your machine or on Nhost Cloud. The difference is only which project the assistant is pointed at, and how much it is allowed to do there.

The dashboard still matters, but as the place you go to **check** what happened rather than the place you click through to make it happen.

## 1. Connect an assistant

Everything below assumes your assistant can reach an Nhost project over MCP. Set that up first:

For a local project, give the assistant full access. Nothing there is real, and the faster loop is worth more than the guardrails. For a project on Nhost Cloud, start read-only and widen deliberately.

## 2. Start a project

Ask the assistant to set one up rather than running anything yourself:

> Set up a new Nhost project here and start it locally.

It runs `nhost init` and `nhost up`, which brings up Postgres, the GraphQL API, Auth, and Storage in Docker. If you would rather build against Nhost Cloud, create the project at [app.nhost.io](https://app.nhost.io) and ask the assistant to pull it down instead:

> Pull my Nhost Cloud project into this directory.

That runs `nhost init --remote`, which fetches the project's configuration, migrations, and metadata into a local `nhost/` directory you can commit.

## 3. Describe your schema

Tables, columns, and relationships are things you can ask for in words:

> Add a movies table with a title, director, release year, genre, and a rating. Titles are required.

The assistant creates the table and writes a migration file for it. Ask to see the migration before you move on; that file is what will run against every other environment, and reading it is the fastest way to catch a column type or a nullability choice you did not intend.

:::caution
A table that exists in Postgres is not automatically exposed through the GraphQL API. If a new table does not show up in your queries, ask the assistant to track it.
:::

## 4. Set permissions

New tables are readable by nobody until you say otherwise. Describe the rule rather than filling in a matrix:

> Let signed-in users read all movies, and only let them update rows they created.

Permissions are the security boundary for your project. Every request through the GraphQL API runs under a role and is filtered by these rules, including the requests your assistant makes. This is the one step worth verifying by hand: open **Database → Permissions** in the dashboard and read back what was applied. See [Permissions](/products/graphql/permissions) for the rule syntax and [permission variables](/products/graphql/permissions/permission-variables) for user-scoped rules.

## 5. Connect your app

Ask for the client setup and the assistant will install the SDK and wire it up:

> Add the Nhost SDK to this app and connect it to my project.

```js
import { createClient } from "@nhost/nhost-js";

export const nhost = createClient({
  subdomain: "<subdomain>",
  region: "<region>",
})
```

Every service is addressed from that same subdomain and region, so the SDK builds the URLs for you:

| Service | URL |
|---------|-----|
| **GraphQL** | `https://<subdomain>.graphql.<region>.nhost.run/v1` |
| **Auth** | `https://<subdomain>.auth.<region>.nhost.run/v1` |
| **Storage** | `https://<subdomain>.storage.<region>.nhost.run/v1` |
| **Functions** | `https://<subdomain>.functions.<region>.nhost.run/v1` |

For a local project both values are `local`. For a cloud project they are on the project's overview page. The [quickstarts](/getting-started/quickstart/react) walk this through end to end for React, Next.js, Vue, SvelteKit, and React Native.

## 6. Configure auth and secrets

Sign-in methods, email templates, redirect URLs, environment variables, and secrets are all project configuration, which the assistant can read and change when you let it:

> Enable email and password sign-in, and set the client URL to localhost:3000.

Set the **Client URL** to where your app runs, and list every origin your app redirects back to; auth flows reject redirects to URLs that are not listed. See [Client and redirect URLs](/products/auth/client_and_redirect_urls), [environment variables](/platform/cloud/environment-variables), and [secrets](/platform/cloud/secrets).

:::caution
Secrets are the one thing worth setting yourself. Ask the assistant which variables a service needs, then put the values in through the dashboard so the real credential never passes through a chat transcript.
:::

## 7. Review and commit

This is what makes the workflow durable rather than a pile of untracked clicks. The assistant writes real files:

- **Migrations** under `nhost/migrations/`, one per schema change
- **Metadata** under `nhost/metadata/`, covering permissions, relationships, and tracked tables
- **Configuration** in `nhost.toml`

Read them, then commit. From there the project is reproducible: another developer runs `nhost up` and gets the same backend, and [deployments](/platform/cloud/deployments) apply the same migrations to Nhost Cloud.

If you skip this step and let changes accumulate only on the server, you lose the thing that makes the rest of it work. Ask the assistant to show you a diff whenever you are not sure what changed.
