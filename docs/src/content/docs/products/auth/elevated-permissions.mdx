In some scenarios you may want to add an extra layer of security to perform certain actions or view certain data. For instance, you may allow users to view their profile information after signing in but require them to confirm profile changes with WebAuthn, TOTP, an email OTP, or an SMS OTP.

![overview-flow](/images/auth/elevated-permissions/overview.png)

This is accomplished by adding the claim `x-hasura-auth-elevated: $user-id` to the access token in response to the extra security challenge. With this new claim in mind you can start writing permissions that require this extra step.

It is important to keep in mind the claim is added to the access token so, for as long as you have that access token, you will have elevated access. Once the access token is renewed (due to expiration or any other reason), the claim will be lost and a new security challenge will be required to add it back.

# API endpoints and SDK methods

Every elevation endpoint requires an `Authorization` header with a valid access token. Which factors are available depends on the Auth configuration and the factors enrolled on the current user's account.

## WebAuthn

Enable WebAuthn with `auth.method.webauthn.enabled = true` in `nhost.toml` or `AUTH_WEBAUTHN_ENABLED` in the environment, and register a security key on the user's account. Elevation first requests a challenge from [`POST /elevate/webauthn`](/reference/auth/post-elevate-webauthn) with [`nhost.auth.elevateWebauthn()`](/reference/javascript/nhost-js/auth#elevatewebauthn), then verifies the signed challenge with [`POST /elevate/webauthn/verify`](/reference/auth/post-elevate-webauthn-verify) or [`nhost.auth.verifyElevateWebauthn()`](/reference/javascript/nhost-js/auth#verifyelevatewebauthn).

## TOTP

Enable MFA with `auth.totp.enabled = true` in `nhost.toml` or `AUTH_MFA_ENABLED` in the environment; the user must also have an active TOTP factor. TOTP elevation is a single request to [`POST /elevate/totp`](/reference/auth/post-elevate-totp) using [`nhost.auth.elevateTotp()`](/reference/javascript/nhost-js/auth#elevatetotp).

## One-time password by email

Enable email OTP with `auth.method.otp.email.enabled = true` in `nhost.toml` or `AUTH_OTP_EMAIL_ENABLED` in the environment; the user must have an email address. Request a code with [`POST /elevate/otp/email`](/reference/auth/post-elevate-otp-email) or [`nhost.auth.elevateOTPEmail()`](/reference/javascript/nhost-js/auth#elevateotpemail), then verify it with [`POST /elevate/otp/email/verify`](/reference/auth/post-elevate-otp-email-verify) or [`nhost.auth.verifyElevateOTPEmail()`](/reference/javascript/nhost-js/auth#verifyelevateotpemail).

## One-time password by text message

Enable SMS passwordless authentication with `auth.method.smsPasswordless.enabled = true` in `nhost.toml` or `AUTH_SMS_PASSWORDLESS_ENABLED` in the environment. Offer SMS elevation only when the session user's `phoneNumber` is non-empty and `phoneNumberVerified === true`; both fields are part of the `User` payload. Both elevation endpoints return `invalid-request` when the signed-in user has no usable phone factor. The `disabled-endpoint` error instead means SMS passwordless authentication is disabled for the project.

Request a code with [`POST /elevate/otp/sms`](/reference/auth/post-elevate-otp-sms) or [`nhost.auth.elevateOTPSms()`](/reference/javascript/nhost-js/auth#elevateotpsms), then verify it with [`POST /elevate/otp/sms/verify`](/reference/auth/post-elevate-otp-sms-verify) or [`nhost.auth.verifyElevateOTPSms()`](/reference/javascript/nhost-js/auth#verifyelevateotpsms). Neither endpoint accepts a phone number. Auth always sends the code to the signed-in user's stored, verified phone number.

Setting `phoneNumber` alone doesn't make SMS an elevation factor. Auth marks the phone number as verified only after successful SMS OTP verification.

WebAuthn, email OTP, and SMS OTP use a two-step challenge or send-and-verify flow. TOTP verifies the code in one step. After successful verification, `nhost-js` automatically persists the returned elevated session.

:::note[OTP behavior]
Wrong, expired, and attempt-exhausted SMS codes all return `invalid-otp`. An email OTP can instead return `otp-too-many-attempts` when its attempt limit is reached.

Both email and SMS challenges share one OTP slot. Requesting an email OTP and an SMS OTP back to back invalidates the earlier code; only the most recently requested code remains valid.
:::

# Protecting Auth data

Some user information needs to be changed via Auth's API rather than via graphql mutations. The operations protected by the elevated claim are:

- [/user/password](/reference/auth/post-user-password) for changing passwords
- [/user/email/change](/reference/auth/post-user-email-change) for changing emails
- [/mfa/totp/generate](/reference/auth/get-mfa-totp-generate) for generating the TOTP secret required to enable MFA. [`POST /user/mfa`](/reference/auth/post-user-mfa) itself requires only a valid access token, so deactivating MFA is not gated by the elevated claim
- [/user/webauthn/add](/reference/auth/post-user-webauthn-add) for starting security key enrollment and [/user/webauthn/verify](/reference/auth/post-user-webauthn-verify) for completing it
- [/pat](/reference/auth/post-pat) for PAT creation
- [/link/idtoken](/reference/auth/post-link-idtoken) for linking an external provider account

To require the elevated claim for the listed protected operations, use the following configuration option:

```toml
[auth.elevatedPrivileges]
mode = 'required'
```

The mode can be one of `disabled` (default), `required`, `recommended`.

In `disabled` mode the elevated claim isn't required for any of the listed protected operations. This is the default behavior.

In `required` mode, the listed protected operations require an access token with the elevated claim, regardless of which factors the user has. The `/user/webauthn/add` and `/user/webauthn/verify` endpoints are routed through the bypass check: enrolling a first security key is exempt only when the user has no other usable elevation factor. For example, a user with a verified phone number on a project with SMS passwordless enabled must elevate with SMS before enrolling the first key. Adding more security keys after the first and removing security keys always require the elevated claim.

In `recommended` mode, the elevated claim is required only when the user has at least one usable elevation factor: a security key while WebAuthn is enabled; an active TOTP factor with a configured secret while MFA is enabled; an email address while email OTP is enabled, provided the address is verified or email verification is not required; or a non-empty, verified phone number while SMS passwordless is enabled. Users without any usable factor can perform the protected operations without the elevated claim.

:::caution[Deploy elevation clients before this Auth version]
This release makes projects using `recommended` mode begin requiring elevation for users with an active TOTP factor and configured secret while MFA is enabled, users with an eligible email address while email OTP is enabled, and users with a verified phone number while SMS passwordless is enabled. An eligible email is any verified address, or any address when email verification is not required, so this is effectively all users on many projects with email OTP enabled. The SMS case includes rows where the project set `auth.users.phone_number_verified` itself through Hasura GraphQL.

Ship clients that offer every enabled elevation method before deploying this Auth version. To opt out, switch the elevation mode to `disabled` or disable each method you are not yet ready to prompt for. Disabling only SMS passwordless is not sufficient when MFA or email OTP remains enabled.
:::

:::caution
If you are allowing users to perform changes to auth data directly by performing graphql mutations (i.e. deleting security keys), don't forget to update the permissions to match the desired behavior.
:::

To demonstrate how the elevated claim can work for permissions you can check the "Secret Notes" example. In this example, we are allowing users to see their secret notes by giving the `select` permissions `notes.user_id eq X-Hasura-User-Id`
