In some scenarios you may want to add an extra layer of security to perform certain actions or view certain data. For instance, you may wish to allow users to view their profile information after authenticating but require them to confirm changes to their profile by performing an extra verification step, such as touching a [security key](/products/auth/webauthn#add-a-security-key), entering a code from their [authenticator app](/products/auth/mfa), or entering a one-time password sent to their email or phone.

![overview-flow](/images/auth/elevated-permissions/overview.png)

This is accomplished by adding the claim `x-hasura-auth-elevated: $user-id` to the access token in response to the extra security challenge. With this new claim in mind you can start writing permissions that require this extra step.

It is important to keep in mind the claim is added to the access token so, for as long as you have that access token, you will have elevated access. Once the access token is renewed (due to expiration or any other reason), the claim will be lost and a new security challenge will be required to add it back.

## Elevation methods

A signed-in user can elevate their session with any of the following methods. A method is only available when it is enabled for the project **and** the user has set it up:

| Method | Enabled with | Available to the user when |
|---|---|---|
| `webauthn` | `auth.method.webauthn.enabled` | They have at least one [security key](/products/auth/webauthn) registered |
| `totp` | `auth.totp.enabled` | They have activated [TOTP](/products/auth/mfa) on their account |
| `otp-email` | `auth.method.otp.email.enabled` | They have an email address |
| `otp-sms` | `auth.method.otp.sms.enabled` | They have a verified phone number |

Every method ends with the same result: a new session whose access token carries the `x-hasura-auth-elevated` claim. The JavaScript SDK stores that session automatically, so subsequent requests made with the same client use the elevated token.

:::note
Enabling `auth.method.otp.email` or `auth.method.otp.sms` also enables the corresponding passwordless sign-in method. Email OTP elevation uses the same `signin-otp` [email template](/products/auth/email-templates) as email OTP sign-in.
:::

### Discovering available methods

Use [`GET /elevate`](/reference/auth/get-elevate) to find out whether the current user needs to elevate their session and which methods they can use:

```js
const { body } = await nhost.auth.getElevationMethods();
// {
//   elevationRequired: true,
//   methods: ['webauthn', 'totp', 'otp-email']
// }
```

- `elevationRequired` tells you whether the [protected auth endpoints](#protecting-auth-data) will require an elevated session for this user under the current mode.
- `methods` lists the methods the user can use right now.

If `elevationRequired` is `true` and `methods` is empty, the user has to set up a second factor before they can perform any protected action.

All elevation endpoints require an `Authorization` header with a valid access token for the user being elevated.

## Protecting Auth data

Some user information needs to be changed via Auth's API rather than via GraphQL mutations. These endpoints are:

- [/user/password](/reference/auth/post-user-password) for changing passwords
- [/user/email/change](/reference/auth/post-user-email-change) for changing emails
- [/user/phone-number/change](/reference/auth/post-user-phone-number-change) and [/user/phone-number/change/verify](/reference/auth/post-user-phone-number-change-verify) for changing phone numbers
- [/mfa/totp/generate](/reference/auth/get-mfa-totp-generate) for setting up TOTP
- [/user/webauthn/add](/reference/auth/post-user-webauthn-add) and [/user/webauthn/verify](/reference/auth/post-user-webauthn-verify) for adding security keys
- [/pat](/reference/auth/post-pat) for PAT creation
- [/link/idtoken](/reference/auth/post-link-idtoken) for linking an identity provider account

To protect these endpoints and require the elevated claim you can use the following configuration option:

```toml title="nhost.toml"
[auth.elevatedPrivileges]
mode = 'required'
```

The mode can be one of `disabled` (default), `recommended`, `required`.

In `disabled` mode the elevated claim isn't required for any of the endpoints above. This is the default behavior.

In `recommended` mode, the elevated claim is only required if the user has at least one [elevation method](#elevation-methods) available. Users with no available method can perform the actions above without elevating. This mode lets users opt into the extra security by setting up a second factor.

:::caution
In `recommended` mode, email OTP and SMS OTP count as available methods too. If you enable `auth.method.otp.email`, every user with an email address will have to elevate before performing the actions above, which effectively behaves like `required` mode for them.
:::

In `required` mode, all of the endpoints above require an access token with the elevated claim. The only exception is setting up a first factor: if the user has no elevation method available, they can register a security key (`/user/webauthn/add` and `/user/webauthn/verify`) or start TOTP setup (`/mfa/totp/generate`) without the elevated claim. Every other endpoint still requires it, so such a user can't perform any other protected action until they set up a factor and elevate their session. Once the user has any method available, setting up additional factors requires the elevated claim as well.

:::caution
If you are allowing users to perform changes to auth data directly by performing GraphQL mutations (i.e. deleting security keys), don't forget to update the permissions to match the desired behavior.
:::
