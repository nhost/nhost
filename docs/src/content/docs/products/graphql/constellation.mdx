**Constellation** turns your Postgres database into a fast, role-based GraphQL API at a fraction of the resources. It is an opt-in, Hasura-compatible alternative for supported GraphQL request-path features, including queries, mutations, subscriptions, remote schemas and cross-source relationships. Compatibility is still being verified during alpha; metadata authoring remains with the existing engine, and some schema and runtime differences are documented below. The rest of these docs call the supported request path the GraphQL API; consult the support matrix and known differences for engine-specific behavior.

:::caution[Alpha and opt-in]
Constellation is in **alpha** and **opt-in** today. It runs alongside Hasura rather than replacing it, so you can switch it on, send real traffic through it, and turn it back off whenever you like. It will become the default over time. See the [announcement](https://nhost.io/blog/introducing-constellation) for the full story.
:::

## Why Constellation

The GraphQL engine shouldn't be the most expensive thing in your stack. Running the same production traffic, Constellation uses [~90% less memory](https://nhost.io/blog/introducing-constellation#early-production-results) than Hasura, with comparable or slightly lower CPU and latency. And that's before the performance work still on the roadmap.

## Enabling Constellation

Add an `[experimental.constellation]` block to your project's `nhost.toml`, either locally or in your cloud project's configuration editor:

```toml title="nhost.toml"
[experimental.constellation]
# Pick the latest tag from the CHANGELOG. We recommend always running the latest.
# https://github.com/nhost/nhost/blob/main/services/constellation/CHANGELOG.md
version = "0.7.0"

[experimental.constellation.settings]
# CORS allowed origins. If unset, origins are derived from
# auth.redirections.clientUrl and auth.redirections.allowedUrls.
# Entries may use "*" as a wildcard (e.g. "https://my-app-*-org.vercel.app").
corsAllowedOrigins = []

# Enable debug logging.
debug = false

# Return raw connector/database error detail to clients instead of the
# sanitized generic message. Development only; never enable in production.
devMode = false

# Polling interval for GraphQL subscriptions.
subscriptionPollInterval = "1s"
```

With this in place, your project runs both engines side by side, sharing the same database and metadata:

| Endpoint | Served by |
|---|---|
| `https://<subdomain>.graphql.<region>.nhost.run` | **Constellation** |
| `https://<subdomain>.hasura.<region>.nhost.run` | The existing engine (metadata authoring + anything Constellation doesn't serve yet) |

Remove the `[experimental.constellation]` block to fall straight back to the existing engine.

## What Constellation serves

Constellation serves these **GraphQL request-path** features; computed fields remain a partial PostgreSQL feature. Check each role's SDL and query results before routing production traffic:

- PostgreSQL and SQLite connectors
- Queries, mutations, and subscriptions
- JWT and admin-secret authentication
- Role-based [permissions](/products/graphql/permissions) (row- and column-level, presets, session variables)
- [Remote schemas](/products/graphql/remote-schemas) and cross-source remote relationships
- PostgreSQL scalar computed-field selections, argument-free `where`/`order_by` inputs, and eligible aggregate outputs, with role-specific grants and bound function arguments. Argument-free scalar computed fields are also enforced in role select/update/delete filters and insert/update checks, independently of selection grants. Hasura omits argument-bearing computed fields from row `where`/`order_by` and scalar computed fields from aggregate-order inputs; Constellation matches those omissions. Scalar aggregate outputs include eligible comparable fields in `min`/`max` and numeric fields in all eight numeric aggregate operators, retaining `args`.
- Domain, enum, composite, range, multirange and PostgreSQL arrays (including user-defined enum arrays) as computed arguments use string-only custom scalars, including on tracked-table fields. A public enum accepts bare `happy` and quoted `"happy"`; a public enum array instead requires a quoted PostgreSQL array literal such as `"{happy}"` (bare `happy` is malformed). Numeric/list inputs fail parsing; null/default and invalid-label behavior is pinned. The nonpublic enum parser accepts tokens but pinned Hasura fails runtime value requests, so only Constellation qualified-cast execution is claimed. Constellation binds values through qualified PostgreSQL casts. Pinned Hasura v2.50.3-ce exposes non-public custom argument types but fails string-valued selections with `type "…" does not exist`; Constellation intentionally executes them instead. See [known differences](https://github.com/nhost/nhost/blob/main/services/constellation/KNOWN_DIFFERENCES.md) for scope and limits.
- PostgreSQL table-valued computed-field selections (`SETOF` or a single tracked-table composite return), including nested and mutation/subscription row results. The returned table's select permission controls field visibility and row/column access; `args`, `where`, `order_by`, `distinct_on`, `limit` and `offset` apply within each function result. Hasura exposes no aggregate selection sibling on these fields. A single composite function returning SQL NULL or no row may yield a list with one all-null object for unfiltered roles; target row filters can yield an empty list instead. `SETOF text`, `numeric`, `int4`, `float8`, `bool`, `date`, `uuid`, `jsonb` and installed `public.citext` are exposed as nullable scalars with argument-free row boolean/order and eligible aggregate inputs. Zero-row direct selections yield null parents; multi-row direct selections and even zero/one-row predicates error, while ordering may omit or duplicate parents. Scalar SETOF returning zero yields a null single-object result or a null element per affected row in a collection (the write persists); multi-row returning fails with a sanitized production error (raw SQLSTATE 21000 in dev) and rolls back all same-source writes. When a scalar SETOF aggregate is selected, `count`, column aggregates, computed operands and `nodes` use the same expanded rows, including nested and per-key grouped results; multiple operands expand in lockstep. UUID min/max are advertised but fail where PostgreSQL lacks those functions (42883), as on pinned Hasura. Vector, spatial, array and other untested BASE scalar `SETOF` types remain gated. For a PUBLIC computed-argument enum whose name conflicts with a tracked table object, pinned Hasura v2.50.3-ce atomically rejects metadata replacement; Constellation instead accepts metadata but records an inconsistency and omits only the ambiguous computed selection, keeping unrelated roots and grants. Other type-name collision permutations are not claimed Hasura-equivalent (see known differences). Exact computed `<rel>_aggregate` sibling collisions omit only the ambiguous computed selection/grant, retaining the genuine relationship/aggregate and unrelated role roots; pinned Hasura v2.50.3-ce emits duplicate row and order input names instead (see known differences). Argument-free table functions also support row boolean EXISTS and `<field>_aggregate` ordering with the returned table's select row filter (matching patched Hasura v2.50.3-ce); metadata role filters/checks can reference them independently of a target select grant.
- No-user-argument, non-SETOF PostgreSQL scalar computed fields can key remote `to_source` object/array joins (text or JSONB objects, strings, numbers and arrays with a matching target column) and text→remote-schema `ID!` joins, including session-bound functions. The role needs the computed field's select grant. Unlike Hasura v2.50.3-ce, a role without that grant neither sees nor uses the relationship; Constellation also requires select access to the computed `to_source` join's target column to prevent an equality oracle on its hidden value. Target row filters still apply. Physical-key relationships do not use these computed-key authorization gates; JSONB targets bind typed JSON values for object/array joins, including physical keys whose target column is role-hidden; JSONB array `_aggregate` siblings also bind and stitch typed keys for computed and physical JSONB keys. PostgreSQL `json` target columns have no `json = json` operator: ordinary and grouped joins into them fail at execution, as in Hasura’s equality join. GeoJSON object keys are JSON-encoded, fixing physical geometry joins. Argument-bearing, table-valued and scalar `SETOF` keys and all JSON/JSONB computed keys toward remote schemas are unavailable, regardless of remote argument type. Scalar `SETOF`-keyed relationships are omitted for all roles, including admin, without an inconsistency. A restored Hasura v2.50.3-ce probe exposed a `SETOF text`-keyed `to_source` relationship even for ungranted roles; Constellation intentionally omits it to avoid a role-hidden or multi-valued join key. Other SETOF key shapes are unprobed.

## What still runs on Hasura

While Constellation is opt-in, metadata authoring and everything **off** the request path continue to be served by the existing engine, so nothing breaks when you flip Constellation on. These are not yet implemented in Constellation:

- Metadata authoring API (the existing engine remains the source of truth for metadata)
- [Events](/products/events): event triggers and cron/scheduled triggers
- Actions, REST endpoints, allowlists, query collections
- Inherited roles and native queries
- MSSQL / BigQuery / Snowflake backends

Database errors in computed arguments and columns keep Constellation's production sanitizer; dev mode returns the raw error chain, not Hasura v2.50.3-ce's code/path envelope. Constellation also rejects quoted-string GraphQL `Int` inputs in both paths **where Hasura accepts and executes them**; floats and out-of-range Int values have different error presentations. These are narrow inherited differences, not universal parity claims; see [the tested scope](https://github.com/nhost/nhost/blob/main/services/constellation/KNOWN_DIFFERENCES.md#inherited-database-error-sanitization-and-strict-int-inputs-approved-phase-14).

For the field-by-field map of what carries across and what is silently dropped, see the **[metadata support matrix](https://github.com/nhost/nhost/blob/main/services/constellation/docs/user/hasura-metadata-support.md)**. Constellation reads computed definitions and grants but does not author them: add/drop and other metadata writes go to the existing Hasura engine when an upstream is configured. Without one, those operations are unsupported. Native database-snapshot export can show polled metadata before a successful served-schema reload, so verify the affected role's SDL and data after changes; to roll back, repair the metadata and reload or disable Constellation.

## Verifying compatibility

Because both engines run against the same database and metadata, you can confirm Constellation generates the schema you expect by diffing the two endpoints per role with the Nhost CLI:

<Steps>

1. **Dump each role's schema from both endpoints**

   ```bash
   nhost schema dump --role user --subdomain <subdomain> \
     -u "https://<subdomain>.hasura.<region>.nhost.run/v1/graphql" \
     -o schema.existing.user.graphqls

   nhost schema dump --role user --subdomain <subdomain> \
     -u "https://<subdomain>.graphql.<region>.nhost.run/v1/graphql" \
     -o schema.constellation.user.graphqls
   ```

2. **Diff them**

   ```bash
   nhost schema diff -a schema.existing.user.graphqls -b schema.constellation.user.graphqls
   ```

   An empty diff means Constellation generated a byte-equivalent schema for that role. Repeat for each role (`admin`, `user`, `public`, and so on).

</Steps>

:::tip
If you've linked a project with `nhost link`, you can drop `-u`/`--admin-secret` and just pass `--role`.
:::

Any non-empty diff should map to a documented, intentional divergence. The full list lives in **[known differences](https://github.com/nhost/nhost/blob/main/services/constellation/KNOWN_DIFFERENCES.md)**. For example, Constellation rejects empty update mutations that the existing engine silently no-ops, and it discovers aggregate support from Postgres rather than hardcoding it. If you find a divergence that isn't documented there, please [open an issue](https://github.com/nhost/nhost/issues/new).
