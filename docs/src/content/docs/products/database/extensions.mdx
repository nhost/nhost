## hypopg

HypoPG is a PostgreSQL extension adding support for hypothetical indexes.

An hypothetical -- or virtual -- index is an index that doesn't really exists, and thus doesn't cost CPU, disk or any resource to create. They're useful to know if specific indexes can increase performance for problematic queries, since you can know if PostgreSQL will use these indexes or not without having to spend resources to create them.

### Managing

To install the extension you can create a migration with the following contents:

```sql
SET ROLE postgres;
CREATE EXTENSION hypopg;
```

To uninstall it, you can use the following migration:

```sql
SET ROLE postgres;
DROP EXTENSION hypopg;
```

### Resources

- [GitHub](https://github.com/HypoPG/hypopg)

## pgvector

Open-source vector similarity search for Postgres. Store your vectors with the rest of your data.

Supports:

- exact and approximate nearest neighbor search
- L2 distance, inner product, and cosine distance
- any language with a Postgres client

Plus ACID compliance, point-in-time recovery, JOINs, and all of the other great features of Postgres

### Managing

To install the extension you can create a migration with the following contents:

```sql
SET ROLE postgres;
CREATE EXTENSION IF NOT EXISTS vector;
```

pg_search 0.25+ may already have installed `vector` through `CASCADE` or the image's startup upgrade, so this migration works when `vector` is already present.

To uninstall it, you can use the following migration:

```sql
SET ROLE postgres;
DROP EXTENSION vector;
```

pg_search 0.25+ depends on `vector`, so this migration fails while pg_search is installed (including when an upgrade installed `vector` for pg_search). If you intend to remove both extensions, first review and explicitly drop any dependent BM25 indexes, then drop pg_search before dropping `vector`. Do not use `DROP EXTENSION vector CASCADE;` as a shortcut: it also drops pg_search and its dependent BM25 indexes.

### Resources

- [GitHub](https://github.com/pgvector/pgvector)

## pg_durable

pg_durable provides SQL-native durable orchestrations that persist their state in PostgreSQL and resume after crashes, restarts, and failovers.

:::caution
This is a limitation of pg_durable: the extension does not register its `df.instances`, `df.nodes`, and `df.vars` tables for logical dumps, so their data is excluded from `pg_dump`. Nhost daily backups, manual `pg_dump`/`pg_restore`, and daily-backup imports into another project therefore do **not** preserve pg_durable workflows. Restoring one loses workflow definitions, status, results, and variables. Engine data in `_duroxide` can still be restored, leaving orphaned engine rows; the background worker can also conflict with `pg_restore` while recreating those objects. [Point-in-time recovery](/products/database/backups#point-in-time-recovery) uses physical backups and preserves workflow state.
:::

### Managing

Preload `pg_durable` via `postgres.settings.sharedPreloadLibraries` for its
background worker; the Cloud default list omits it. The extension does not
grant access to `PUBLIC`. To enable it for workflows submitted through Nhost
GraphQL, create this migration:

```sql
SET ROLE postgres;
CREATE EXTENSION pg_durable;
RESET ROLE;
```

In Nhost databases, `nhost_hasura` inherits membership in `postgres`, which owns the `df` objects. It already has full access to pg_durable, so `df.grant_usage('nhost_hasura')` would be redundant. In particular, it can execute `df.http()` and `df.http_multipart()` without an HTTP-specific grant and bypasses row-level security on `df.instances`, `df.nodes`, and `df.vars`: it can see and change workflows submitted by other roles.

After the migration commits, the `df.*` functions exist, but the background worker initializes asynchronously. During the first 1–5 seconds, calls can fail with:

```text
pg_durable background worker not yet initialized — try again in a moment
```

Retry the call after a short delay.

Nhost leaves `pg_durable.enable_superuser_instances` at its default of `off`. Workflows must therefore be submitted by a non-superuser role with `LOGIN`, because the background worker reconnects as the role captured by `df.start()`. Do not submit as `postgres` or `nhost_admin`; both are superusers and `df.start()` rejects them. The `nhost_hasura` role used by Nhost GraphQL is a non-superuser `LOGIN` role, but it can `SET ROLE postgres`; this setting does not restrict the SQL its workflows can run.

To enforce per-role isolation and HTTP opt-in, submit workflows through a direct PostgreSQL connection as a dedicated login role that is not a member of `postgres`, rather than through Nhost GraphQL as `nhost_hasura`. For example, create a least-privileged role in the installation migration:

```sql
SET ROLE postgres;
CREATE ROLE durable_executor
  LOGIN
  NOSUPERUSER
  NOCREATEDB
  NOCREATEROLE
  NOREPLICATION
  NOBYPASSRLS;
SELECT df.grant_usage('durable_executor');
RESET ROLE;
```

Configure authentication for the role through your normal secrets workflow rather than committing credentials in a migration. Grant it only the additional table and function privileges required by its workflow SQL.

:::caution
For security, Nhost disables pg_durable's SQL-step logging by default (`PG_DURABLE_LOG_WORKFLOW_SQL=off` sets `pg_durable.log_workflow_sql` to `off`). This prevents the worker from logging SQL after `{var}` substitution, but it does **not** disable all logging: submitted `df.start()` statements and final workflow results, including HTTP response bodies, can still appear in the Database logs available to project members with log access. Keep credentials out of workflow definitions and results, and do not assume `df.setvar()` makes secrets safe to include in logged statements or results.
:::

### HTTP egress and access control

Nhost builds pg_durable with the `http-allow-all` feature, enabling unrestricted HTTP destinations. `df.http()` and `df.http_multipart()` can contact any HTTP or HTTPS destination reachable from PostgreSQL. Fresh pg_durable installations revoke execution of both HTTP functions from `PUBLIC`. For roles that do not inherit `postgres`, `df.grant_usage` without `include_http => true` does not grant HTTP execution; a database administrator must explicitly opt them into HTTP egress:

```sql
SET ROLE postgres;
SELECT df.grant_usage('app_role', include_http => true);
```

Equivalent direct `GRANT EXECUTE` statements can grant either HTTP function more narrowly. Do not grant HTTP execution to roles that do not require outbound network access. Workflows submitted through Nhost GraphQL run as `nhost_hasura`, which inherits HTTP execution from `postgres`; they can always make HTTP requests without this grant.

To uninstall the extension, use the following migration:

```sql
SET ROLE postgres;
DROP EXTENSION pg_durable CASCADE;
```

`CASCADE` is required and removes pg_durable's workflow state. Wait at least 20 seconds before recreating the extension so its background worker can shut down fully.

## pg_ivm

The pg_ivm module provides Incremental View Maintenance (IVM) feature for PostgreSQL.

Preload `pg_ivm` via `postgres.settings.sharedPreloadLibraries` for incremental
view maintenance across sessions; the Cloud default list omits it. Alternatively,
preload it in each session with `session_preload_libraries`.

Incremental View Maintenance (IVM) is a way to make materialized views up-to-date in which only incremental changes are computed and applied on views rather than recomputing the contents from scratch as REFRESH MATERIALIZED VIEW does. IVM can update materialized views more efficiently than recomputation when only small parts of the view are changed.

### Managing

## pg_repack

pg_repack is a PostgreSQL extension which lets you remove bloat from tables and indexes, and optionally restore the physical order of clustered indexes. Unlike CLUSTER and VACUUM FULL it works online, without holding an exclusive lock on the processed tables during processing. pg_repack is efficient to boot, with performance comparable to using CLUSTER directly.

### Managing

To install the extension you can create a migration with the following contents:

```sql
SET ROLE postgres;
CREATE EXTENSION pg_repack;
```
In addition, you may need to configure the WAL level and replication slots. Check the official documentation for details.

To uninstall it, you can use the following migration:

```sql

DROP EXTENSION pg_repack;
```

## pg_search

pg_search is a Postgres extension that enables full text search over heap tables using the BM25 algorithm. It is built on top of Tantivy, the Rust-based alternative to Apache Lucene, using pgrx.

Preload `pg_search` via `postgres.settings.sharedPreloadLibraries` before using BM25 search.

### Managing

pg_search 0.25+ requires pgvector (`vector`). To install both extensions in a fresh database, create a migration with the following contents:

```sql
SET ROLE postgres;
CREATE EXTENSION pg_search CASCADE;
```

`CASCADE` installs `vector` if it is not already installed. Dropping pg_search does not remove `vector`.

To uninstall pg_search, you can use the following migration:

```sql
SET ROLE postgres;
DROP EXTENSION pg_search;
```
