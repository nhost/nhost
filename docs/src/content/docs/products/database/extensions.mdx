## hypopg

HypoPG is a PostgreSQL extension adding support for hypothetical indexes.

An hypothetical -- or virtual -- index is an index that doesn't really exists, and thus doesn't cost CPU, disk or any resource to create. They're useful to know if specific indexes can increase performance for problematic queries, since you can know if PostgreSQL will use these indexes or not without having to spend resources to create them.

### Managing

To install the extension you can create a migration with the following contents:

```sql
SET ROLE postgres;
CREATE EXTENSION hypopg;
```

To uninstall it, you can use the following migration:

```sql
SET ROLE postgres;
DROP EXTENSION hypopg;
```

## postgis_tiger_geocoder

The TIGER geocoder provides address normalization, geocoding, and reverse geocoding for US addresses.

### Managing

To install the extension you can create a migration with the following contents:

```sql
SET ROLE postgres;
CREATE EXTENSION IF NOT EXISTS postgis;
CREATE EXTENSION IF NOT EXISTS fuzzystrmatch;
CREATE EXTENSION IF NOT EXISTS address_standardizer;
CREATE EXTENSION IF NOT EXISTS address_standardizer_data_us;
CREATE EXTENSION IF NOT EXISTS postgis_tiger_geocoder;
RESET search_path;
```

The installer puts `tiger` first in the session's `search_path`. Keep `RESET search_path` immediately after installation to avoid creating later objects in `tiger`.

Fresh installations also need `tiger` in the database `search_path` for geocoder functions to work. As the database owner, replace `your_database` with your database name:

```sql
ALTER DATABASE your_database SET search_path = "$user", public, tiger;
```

If you use a custom path, preserve its schemas and append `tiger` after your application schemas. Reconnect for the change to take effect. If a role or client overrides `search_path`, include `tiger` there too.

:::note
Nhost automatically upgrades installed TIGER extensions at database startup. Existing databases upgraded from TIGER 3.6 retain their database-level `search_path`. Check `SHOW search_path;` in a new connection; if `tiger` is already included, no path change is needed.
:::

To uninstall it, you can use the following migration:

```sql
SET ROLE postgres;
DROP EXTENSION postgis_tiger_geocoder;
```

## pgvector

Open-source vector similarity search for Postgres. Store your vectors with the rest of your data.

Supports:

- exact and approximate nearest neighbor search
- L2 distance, inner product, and cosine distance
- any language with a Postgres client

Plus ACID compliance, point-in-time recovery, JOINs, and all of the other great features of Postgres

### Managing

To install the extension you can create a migration with the following contents:

```sql
SET ROLE postgres;
CREATE EXTENSION IF NOT EXISTS vector;
```

pg_search 0.25+ may already have installed `vector` through `CASCADE` or Nhost's automatic upgrade, so this migration works when `vector` is already present.

To uninstall it, you can use the following migration:

```sql
SET ROLE postgres;
DROP EXTENSION vector;
```

pg_search 0.25+ depends on `vector`, so this migration fails while pg_search is installed (including when an upgrade installed `vector` for pg_search). If you intend to remove both extensions, first review and explicitly drop any dependent BM25 indexes, then drop pg_search before dropping `vector`. Do not use `DROP EXTENSION vector CASCADE;` as a shortcut: it also drops pg_search and its dependent BM25 indexes.

## pg_cron

pg_cron is a simple cron-based job scheduler for PostgreSQL (10 or higher) that runs inside the database as an extension. It uses the same syntax as regular cron, but it allows you to schedule PostgreSQL commands directly from the database. You can also use '[1-59] seconds' to schedule a job based on an interval.

Preload `pg_cron` via `postgres.settings.sharedPreloadLibraries` to run scheduled jobs.

### Dashboard

Open **Events** → **SQL Jobs** to enable or disable pg_cron, create and edit SQL jobs, pause schedules, and inspect run history. You can also follow **Manage SQL jobs** from the pg_cron card or row in **Database** → **Extensions** for the default database.

SQL jobs run in the scheduler's configured timezone, unlike [Cron Triggers](/products/events/cron-triggers), which use UTC. The **Settings** tab manages the scheduler timezone, concurrency, and run logging. Use **Create retention job** to open an editable example that removes run-history entries older than seven days, scheduled daily at 05:00 in the scheduler's timezone.

The dashboard saves job and extension changes as Hasura migrations when using the Nhost CLI and runs SQL directly on hosted projects.

Scheduler settings are stored in the project configuration (`[postgres.settings.extensions.cron]` in `nhost.toml`), not in migrations. On hosted projects, saving these settings restarts PostgreSQL and causes a short period of database downtime. With the Nhost CLI, run `nhost up` to restart PostgreSQL and apply the settings. See [Configuring Postgres](/products/database/configuring-postgres) for setting defaults and operational notes.

### Managing

## pg_durable

pg_durable provides SQL-native durable orchestrations that persist their state in PostgreSQL and resume after crashes, restarts, and failovers.

:::caution
This is a limitation of pg_durable: the extension does not register its `df.instances`, `df.nodes`, and `df.vars` tables for logical dumps, so their data is excluded from `pg_dump`. Nhost daily backups, manual `pg_dump`/`pg_restore`, and daily-backup imports into another project therefore do **not** preserve pg_durable workflows. Restoring one loses workflow definitions, status, results, and variables. Engine data in `_duroxide` can still be restored, leaving orphaned engine rows; the background worker can also conflict with `pg_restore` while recreating those objects. [Point-in-time recovery](/products/database/backups#point-in-time-recovery) uses physical backups and preserves workflow state.
:::

### Managing

Preload `pg_durable` via `postgres.settings.sharedPreloadLibraries` before
installing it. The extension does not grant access to
`PUBLIC`. To enable it for workflows submitted through Nhost GraphQL, create
this migration:

```sql
SET ROLE postgres;
CREATE EXTENSION pg_durable;
RESET ROLE;
```

In Nhost databases, `nhost_hasura` inherits membership in `postgres`, which owns the `df` objects. It already has full access to pg_durable, so `df.grant_usage('nhost_hasura')` would be redundant. In particular, it can execute `df.http()` and `df.http_multipart()` without an HTTP-specific grant and bypasses row-level security on `df.instances`, `df.nodes`, and `df.vars`: it can see and change workflows submitted by other roles.

After the migration commits, the `df.*` functions exist, but the background worker initializes asynchronously. During the first 1–5 seconds, calls can fail with:

```text
pg_durable background worker not yet initialized — try again in a moment
```

Retry the call after a short delay.

Nhost leaves `pg_durable.enable_superuser_instances` at its default of `off`. Workflows must therefore be submitted by a non-superuser role with `LOGIN`, because the background worker reconnects as the role captured by `df.start()`. Do not submit as `postgres` or `nhost_admin`; both are superusers and `df.start()` rejects them. The `nhost_hasura` role used by Nhost GraphQL is a non-superuser `LOGIN` role, but it can `SET ROLE postgres`; this setting does not restrict the SQL its workflows can run.

To enforce per-role isolation and HTTP opt-in, submit workflows through a direct PostgreSQL connection as a dedicated login role that is not a member of `postgres`, rather than through Nhost GraphQL as `nhost_hasura`. For example, create a least-privileged role in the installation migration:

```sql
SET ROLE postgres;
CREATE ROLE durable_executor
  LOGIN
  NOSUPERUSER
  NOCREATEDB
  NOCREATEROLE
  NOREPLICATION
  NOBYPASSRLS;
SELECT df.grant_usage('durable_executor');
RESET ROLE;
```

Configure authentication for the role through your normal secrets workflow rather than committing credentials in a migration. Grant it only the additional table and function privileges required by its workflow SQL.

:::caution
For security, Nhost sets `postgres.settings.extensions.pgDurable.logWorkflowSql` to `off` by default (see [Configuring Postgres](/products/database/configuring-postgres)), which sets `pg_durable.log_workflow_sql` to `off` and prevents the worker from logging SQL after `{var}` substitution. Setting it to `on` logs substituted SQL, which may contain secrets; enable it only temporarily for debugging. This does **not** disable all logging: submitted `df.start()` statements and final workflow results, including HTTP response bodies, can still appear in the Database logs available to project members with log access. Keep credentials out of workflow definitions and results, and do not assume `df.setvar()` makes secrets safe to include in logged statements or results.
:::

### HTTP egress and access control

Configure outbound requests from `df.http()` and `df.http_multipart()` with `postgres.settings.extensions.pgDurable.httpSecurity` in your project configuration. It sets PostgreSQL's `pg_durable.http_security` policy:

- **`unrestricted` (default):** allows HTTP and HTTPS to any destination reachable from PostgreSQL, including private networks.
- **`restricted`:** allows HTTPS only to allow-listed hostnames; bare IP URLs and private/internal IP destinations are blocked. The allow-list defaults to empty, which blocks all hosts.
- **`disabled`:** blocks pg_durable HTTP requests.

Set `postgres.settings.extensions.pgDurable.httpAllowedDomains` alongside the restricted policy to allow specific hosts:

```toml title="nhost.toml"
[postgres.settings.extensions.pgDurable]
httpSecurity = "restricted"
httpAllowedDomains = ["api.example.com", "*.example.org"]
```

`httpAllowedDomains` defaults to `[]`. Use one hostname or `*.domain` subdomain pattern per item, not URLs or comma-separated strings. The array replaces the entire host allow-list, so include every required destination. It is ignored in `unrestricted` mode.

Changing these server-wide settings requires a PostgreSQL restart. Check workflow destinations before switching to `restricted`: requests to other hosts fail when their HTTP activity executes. TLS verification and redirect blocking remain enforced in enabled modes.

Setting this policy does not enable pg_durable. Add `pg_durable` alongside the other required `postgres.settings.sharedPreloadLibraries` entries and install the extension as described above; HTTP execution privileges are managed separately below.

Fresh pg_durable installations revoke execution of both HTTP functions from `PUBLIC`. For roles that do not inherit `postgres`, `df.grant_usage` without `include_http => true` does not grant HTTP execution; a database administrator must explicitly opt them into HTTP egress:

```sql
SET ROLE postgres;
SELECT df.grant_usage('app_role', include_http => true);
```

Equivalent direct `GRANT EXECUTE` statements can grant either HTTP function more narrowly. Do not grant HTTP execution to roles that do not require outbound network access. Workflows submitted through Nhost GraphQL run as `nhost_hasura`, which inherits HTTP execution from `postgres`; they can make HTTP requests without this grant, subject to the server-wide HTTP policy.

To uninstall the extension, use the following migration:

```sql
SET ROLE postgres;
DROP EXTENSION pg_durable CASCADE;
```

`CASCADE` is required and removes pg_durable's workflow state. Wait at least 20 seconds before recreating the extension so its background worker can shut down fully.

## pg_ivm

The pg_ivm module provides Incremental View Maintenance (IVM) feature for PostgreSQL.

Preload `pg_ivm` via `postgres.settings.sharedPreloadLibraries` for incremental
view maintenance across sessions.

IVM can update materialized views more efficiently than recomputation when only small parts of the view are changed.

### Upgrading to pg_search 0.26

When Nhost upgrades pg_search from a version before 0.26 to 0.26 (including 0.26.7), it automatically rebuilds every ParadeDB index containing a vector field, including unquantized indexes. It removes the obsolete `centroid_ratio`, `training_samples_per_centroid`, `cluster_replication` and `bounds_scope` settings, using the [new clustering defaults](https://www.paradedb.com/docs/project/changelog/0.26.0) (`training_sample_ratio = 0.32`, `max_leaf_size = 100`). Other index configuration and metadata are preserved; each removed setting is logged. Custom clustering tuning is not translated to an equivalent new configuration.

This maintenance blocks writes while rebuilding and can extend startup and consume additional disk space and WAL. Plan the database upgrade as a maintenance window. The extension update and index maintenance commit together: a failure rolls back both and is retried on the next database start. Contact Nhost support if the upgrade keeps failing. Ordinary restarts and updates within 0.26 do not rebuild indexes again.

Review these application-facing changes before upgrading:

- **Check standalone index permissions (0.26.5).** Content-reading APIs such as `paradedb.aggregate()` now require table-level `SELECT` on the backing table and reject calls when row-level security (RLS) applies to the effective caller. See the [0.26.5 release notes](https://www.paradedb.com/docs/project/changelog/0.26.5) for the permission rules, including the separate rules for metadata APIs.

- **Review scores under RLS (0.26.7).** An RLS policy no longer adds a constant to `pdb.score`, so applications relying on absolute scores may see different values. Conditions written in the query itself are unchanged. See the [0.26.7 release notes](https://www.paradedb.com/docs/project/changelog/0.26.7).
