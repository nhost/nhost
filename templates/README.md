# Nhost starter templates

Starter projects for the `nhost create` CLI command:

```sh
npx @nhost/cli create my-app                 # default template
npx @nhost/cli create my-app -t nextjs-shadcn
```

Each template scaffolds a full-stack project:

```
my-app/
  backend/        generated by `nhost init`
    nhost/nhost.toml   backend configuration
    functions/         serverless functions
    .secrets           local secrets
  frontend/       the template's app
  CLAUDE.md  AGENTS.md  SKILLS.md  .mcp.json  README.md  .gitignore
```

## How a template is structured

A template directory is an overlay applied to a generated project. At create time the CLI:

1. generates `backend/` in-process with the same logic as `nhost init` (and enables email OTP + points `clientUrl` at `http://localhost:3000`), then
2. lays the template directory's contents on top. This lets a template add frontend and agent files as well as backend migrations and metadata without duplicating the generated backend.

A template can contain:

```
templates/<name>/
  backend/nhost/ backend migrations and metadata overlaid on the generated backend
  frontend/      a standalone app (real npm deps, its own pnpm-lock.yaml)
  .claude/skills/ reusable agent workflows, one directory per skill
  CLAUDE.md AGENTS.md SKILLS.md .mcp.json README.md .gitignore
```

`frontend/` is intentionally **outside** the pnpm workspace (it is not listed in the root `pnpm-workspace.yaml`) so it resolves published package versions, exactly like a user's generated project. It carries its own `pnpm-workspace.yaml`, which makes it a standalone workspace root, so manage its lockfile with a plain `pnpm install` from inside `frontend/`. Do **not** pass `--ignore-workspace`: that discards the template's own `pnpm-workspace.yaml`, and with it the `allowBuilds` entries that keep `pnpm install --frozen-lockfile` from failing with `ERR_PNPM_IGNORED_BUILDS`.

Both of those files mean nothing to npm, bun, or yarn, so `nhost create --package-manager <pm>` deletes them from the scaffolded project. They are listed in `pnpmOnlyFrontendFiles` (`cli/cmd/create/create.go`) — add any further pnpm-only file in `frontend/` there, or it ships into a project that has no pnpm in it.

## Develop / test a template locally

`--template-path` skips the download and uses a local directory (also how you iterate offline):

```sh
go run ./cli create demo --template-path templates/nextjs-shadcn --no-install
```

Build the template's frontend on its own:

```sh
cd templates/nextjs-shadcn/frontend
pnpm install
pnpm lint && pnpm build
```

CI installs with pnpm 12.3.4. `templates_checks.yaml` passes no `version:` to `pnpm/action-setup`, so the version comes from the root `package.json` `packageManager` field — check there if this drifts. Inside a template the global pnpm runs rather than the version that field pins for the workspace, so verify with `npx pnpm@12.3.4 install --frozen-lockfile` before pushing: pnpm 11 and later fail on ignored build scripts where pnpm 10 only warned.

## Maintainer invariants

- A backend metadata overlay must include `backend/nhost/metadata/version.yaml`. Without it, `nhost up` skips applying the metadata (emitting only a warning), so the table is never tracked.
- Row-level ownership must use an `X-Hasura-User-Id` insert column preset under the permission's `set:` field. Do not use an `auth.uid()` SQL default; clients must not supply the owner column themselves.
- `.mcp.json` must not point the MCP server at the backend with a `cwd` key. `cwd` is not part of the stdio server shape clients accept, so it is dropped and `nhost mcp start` runs from the project root, where it finds no `mcp-nhost.toml` and silently falls back to a default granting the local admin secret plus full query, mutation, and metadata access. Set `NHOST_MCP_CONFIG_FILE` to `backend/.nhost/mcp-nhost.toml` under `env` instead. The `backend` job's "Parse the backend metadata and the MCP config" step in [`templates_checks.yaml`](../.github/workflows/templates_checks.yaml) enforces both halves of this invariant — no `cwd` key on any server, and `mcpServers.nhost.env.NHOST_MCP_CONFIG_FILE` set under `backend/` — so a regression fails CI instead of shipping a silently unscoped admin server.
- A template must ship a project-root `.gitignore`. The generated `backend/.gitignore` (`.nhost`, `.secrets`) comes from `nhost init`, and `frontend/.gitignore` only covers the app directory, so nothing else protects a scaffolded project on its first `git add .`. Keep `.env*` ignored with a `!.env.example` negation in `frontend/.gitignore`: narrowing it to `.env*.local` leaves `.env` and `.env.production` — both loaded by Next.js — tracked.
- Every template must ship the whole agent bundle: `AGENTS.md`, a byte-identical `CLAUDE.md`, `SKILLS.md`, and at least one `.claude/skills/<name>/SKILL.md`. [`check-agent-context.sh`](check-agent-context.sh) treats a directory holding `frontend/package.json` as a template and requires all four, so a template that ships none of them fails rather than passing unnoticed — and an empty `.claude/skills/` with no shipped skills fails the same way, rather than passing with zero workflows checked.
- `SKILLS.md` and `.claude/skills/*/SKILL.md` hold the same four workflows in two layouts: one file for any agent, and the per-skill directories Claude Code discovers. Change a workflow in both, the same way `AGENTS.md` and `CLAUDE.md` are kept identical. The same script enforces both halves — run it before pushing, and the `agent-context` job in [`templates_checks.yaml`](../.github/workflows/templates_checks.yaml) runs it on every PR. A `SKILL.md` body matches its `## <Title>` section of `SKILLS.md` once the YAML frontmatter and the `# Title` line are stripped and every `##` subheading is demoted to `###`; surrounding blank lines are not significant.
- Write every package-manager command in the shipped Markdown as a literal `pnpm <script>`, where `<script>` is `install` or a script in `frontend/package.json`. `nhost create --package-manager <pm>` rewrites those commands (`retargetPackageManagerDocs` in `cli/cmd/create/postprocess.go`) so a project created with npm, bun, or yarn is not told to run pnpm and recreate the lockfile the CLI just removed. Other spellings — `pnpm run <script>`, `npx`, `pnpm --filter ...` — are left untouched and silently ship pnpm instructions to a non-pnpm project. Prose must not name pnpm at all, for the same reason: the rewrite only reaches command invocations, so a prerequisite such as "Node.js >= 22 and [pnpm](https://pnpm.io)" survives into an npm project and leads the reader to exactly the `pnpm install` the rewrite exists to prevent. Write the requirement package-manager-neutral instead. `TestCreateRetargetsRealTemplateDocs` fails on any `pnpm` left in the scaffolded Markdown other than the `pnpm-lock.yaml` filename in the functions runtime's lockfile-precedence rule.
- `frontend/schema.graphql` is both the graphql-codegen input and committed project context for LLMs. After starting the backend with `nhost up`, regenerate the SDL and generated types with `(cd frontend && pnpm codegen)` and commit both `schema.graphql` and `src/gql/`.
- CI's primary offline guard runs `pnpm codegen:types` and requires no diff under committed `src/gql/`. Do not add `nhost schema dump --metadata` as an offline gate: it needs a resolvable database to determine column types. Verify SDL-versus-live-backend fidelity manually by running `nhost up` followed by `pnpm codegen` and reviewing the generated changes.
- The `backend` job covers the other half of a template: `npm ci && ./node_modules/.bin/tsc --noEmit` over `backend/functions/` (which carries its own `package.json`, `package-lock.json`, and strict `tsconfig.json`, so nothing else type-checks the example users copy), plus a parse of every `backend/nhost/metadata/**` YAML and of `.mcp.json`. A permission rule is a YAML document; a typo in one quietly changes who can read what.
- `backend/functions/` must keep `typescript` in its `devDependencies`, and the type-check must invoke `./node_modules/.bin/tsc` rather than `npx tsc`. A runner has no global TypeScript, so `npx tsc` downloads `tsc` from the registry — an unrelated squatted package that exits 1 with a riddle — and the job can never pass. By path, a missing dependency fails as "No such file or directory" and nothing is fetched.
- Both checks in that job must fail on absence, not just on malformed input: the metadata parse counts the files it read and fails at zero, and `.mcp.json` missing is an error. `rglob` over a directory that is not there yields nothing and raises nothing, which would otherwise report success having checked no permission rules at all. The `.mcp.json` check goes further than parsing: it also fails if `mcpServers` is missing or empty, if any server carries a `cwd` key, or if the `nhost` server's `env.NHOST_MCP_CONFIG_FILE` is unset or does not point under `backend/` — the two properties that decide whether the MCP server is scoped or an unscoped admin default.

## Adding a template

1. Create `templates/<name>/` with a `frontend/` app + the root files (`AGENTS.md`, `CLAUDE.md`, `SKILLS.md`, `.mcp.json`, `README.md`, `.gitignore`). Copy `AGENTS.md`, `CLAUDE.md`, `SKILLS.md`, and `.claude/skills/` from an existing template and adapt the framework-specific parts. The four workflows are the same everywhere, but their text is not: each one names the donor template's example files and frontend paths (`public_todos.yaml`, `backend/functions/avatar.ts`, `frontend/src/lib/nhost/server.ts`). Retarget those at the new template's own examples, and make the identical edit in `SKILLS.md` and in `.claude/skills/<name>/SKILL.md` — `check-agent-context.sh` fails if the two disagree.
2. Generate the lockfile: `cd templates/<name>/frontend && pnpm install`.
3. Add an entry to the registry in `cli/cmd/create/registry.go`.
4. Add the template name to the `matrix.template` list of the `frontend` and `backend` jobs in `.github/workflows/templates_checks.yaml`. Both derive their paths from it. `templates/check-ci-matrix.sh`, run by the `agent-context` job, fails the build if either list is missing an entry for a template that ships a `frontend/package.json`, so a template added here without a matrix entry does not pass unnoticed. The `agent-context` job itself needs no change beyond that — it walks every `templates/*/` that ships a `frontend/package.json`, so the new template's duplicated Markdown is checked as soon as it lands.
5. Add a row to [Available templates](#available-templates) above.

## How templates are delivered

The CLI fetches templates from the Nhost monorepo with a shallow, blobless, sparse git checkout of `templates/<name>/`, copies that subtree into the generated project, then removes the temporary clone. Generated projects do not receive the templates repository's `.git` directory.

By default, templates are fetched from `https://github.com/nhost/nhost` at the tag the CLI itself was released from (`cli@<version>`), so a released CLI always scaffolds the template it shipped with. A dev build of the CLI (`0.0.0-dev`) fetches from `main`. Override the source with `--templates-repo` / `NHOST_CREATE_TEMPLATES_REPO` and `--templates-ref` / `NHOST_CREATE_TEMPLATES_REF` when testing a branch or local fixture.

[`templates_checks.yaml`](../.github/workflows/templates_checks.yaml) builds and lints templates on PRs.

## Try a template locally

Use `--template-path` to scaffold from a local checkout without fetching from git:

```sh
npx @nhost/cli create demo --template-path templates/nextjs-shadcn
cd demo/backend && nhost up           # start the local backend
cd demo/frontend && pnpm dev          # http://localhost:3000, OTP sign-in
```
