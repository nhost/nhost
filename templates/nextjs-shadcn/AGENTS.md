# Agent guide

This is a full-stack Nhost project generated by `nhost create`. The committed schema and local skills are the primary project context for coding assistants.

## How to read this guide

Two kinds of thing are written down here, and it is worth knowing which one you are reading. **Primary development loop**, **Project conventions**, **Live data** and **Key commands** are rules: they hold for anything built in this project. Every section whose heading begins with **Example** is one shipped feature's design, kept because copying a working thing is easier than assembling one from principles. Each of those opens by stating the general rule it demonstrates, and each is discardable once you have taken that rule.

The distinction matters most for the public-read example. It is the longest passage in this file, and it is careful security work for exactly one feature: a shared profile page. If what you are building has no unauthenticated surface, take the rule at the top of that section and skip the rest of it wholesale, rather than reproducing a permission model your product does not need. A guide weighted towards one example is a guide that will suggest that example for everything, and this is the note that says not to.

## Stack and layout

- `backend/` is an Nhost project with authentication, PostgreSQL, a GraphQL API, storage, serverless functions, SQL migrations, and GraphQL metadata.
- `frontend/` is a Next.js 16 App Router application using React 19, TypeScript, Tailwind CSS v4, shadcn/ui, `@nhost/nhost-js`, and TanStack Query.
- `backend/functions/avatar.ts` is the shipped serverless function: it authenticates the caller, resizes the uploaded photo, stores it through the storage API as admin, and writes the URL back over GraphQL.
- `frontend/schema.graphql` is both the GraphQL codegen input and the committed backend contract an LLM should read — but it is dumped for the `user` role only. A document sent through `createAnonymousClient()` (see "Example: data readable without a session" below) type-checks against this file even though it executes as `public`, so `pnpm codegen:types` passing does not mean the `public` role can actually read every field the document selects; check the role's column allowlist in `backend/nhost/metadata/` instead.
- `frontend/src/gql/` contains committed generated GraphQL types and typed documents.
- `.claude/skills/` contains repeatable workflows for tables, permissions, functions, and project-context refreshes.

## Primary development loop

Complete the one-time frontend setup first:

```sh
(cd frontend && cp .env.example .env.local && pnpm install)
```

Then use this loop for data-backed features:

1. Start the backend in one terminal:

   ```sh
   (cd backend && nhost up)
   ```

2. After every database schema or GraphQL metadata change, refresh the committed schema and generated types in another terminal:

   ```sh
   (cd frontend && pnpm codegen)
   ```

3. Prompt the LLM with the feature request. The LLM must read `frontend/schema.graphql`, this guide, and the relevant `.claude/skills/<name>/SKILL.md` before editing.
4. Run the narrow frontend checks that match the change, such as `(cd frontend && pnpm lint)`, `(cd frontend && pnpm test)` and `(cd frontend && pnpm build)`.

The committed `frontend/schema.graphql` and `frontend/src/gql/` let an assistant understand and type-check the current data contract without installing another context service. Keep both artifacts in sync with backend changes.

## Skills

Use these workflows rather than inventing paths or metadata shapes:

- `add-table`: add reversible SQL migrations, track a table, configure row-level permissions, and run codegen — in either the per-user or the group-membership ownership shape, and it opens by helping you pick.
- `add-permission`: change role and row access on an existing tracked table, then run codegen.
- `create-function`: add and inspect a file-routed serverless function.
- `refresh-context`: refresh the committed role-scoped schema and generated document types.

They ship in two places with the same content. Read whichever suits the agent:
`SKILLS.md` holds all four in one file, and `.claude/skills/<name>/SKILL.md` is
the per-skill layout Claude Code discovers and loads on its own. Update both
when a workflow changes.

## Example: per-user data — the shipped todos feature

**The rule this demonstrates.** A feature whose rows belong to one person each is a reversible migration, tracked metadata whose row filter names the owner, an insert preset that supplies that owner from the session, refreshed schema and types, and typed documents sent through TanStack Query. Never accept an owner id from the browser: set it from `X-Hasura-User-Id` and keep the column out of every writable list. That rule is the whole of it, and the `add-table` skill applies it to a table of your own.

What follows is the same rule as one working feature, so it can be read rather than assembled. `public.todos` is the shipped example, with row-level `user` permissions:

- `backend/nhost/migrations/default/1700000000000_init_todos/` creates and rolls back the whole feature in one step: the table (`location`, `preposition`, `is_public`, `sort_order`, `file_id`, `created_at`, `updated_at`), the `user_id` and `file_id` indexes, the `touch_updated_at` trigger, and the `todo-attachments` bucket. Keep it one migration when extending the starter **until you have deployed** — until then there is no history to preserve, and the finished shape of the table should be readable in one file. After a deploy that reverses: a migration another environment has already applied cannot be rewritten, so every later change to this table is a new migration like any other. A brand-new table is always a new migration either way — see the `add-table` skill.
- `backend/nhost/metadata/databases/default/tables/public_todos.yaml` tracks the table, presets row ownership on insert, and filters all operations to the current user.
- `backend/nhost/metadata/databases/default/tables/tables.yaml` includes tracked table metadata files.
- `frontend/src/app/protected/Todos.tsx` defines typed `GetTodos` and `CreateTodo` operations, sends them through `@nhost/nhost-js`, and manages request state with TanStack Query.
- `frontend/src/lib/graphql.ts` is the typed request helper shared by data-backed UI.

Per-user ownership is not the only shape. Data a group shares belongs to a membership table rather than to a column on the row, and the `add-table` skill documents both; reaching for `user_id` when the answer is "whoever is on this team" is the commonest way to get a schema wrong on the first try.

## Example: data readable without a session — the shipped shared profile

**The rule this demonstrates.** Public data is a different problem from per-user data, and the difference is that nothing filters by the caller. Every restriction therefore has to live in the permission itself: gate on switches the owner controls, repeat a related table's condition instead of leaning on it, and write a separate, shorter column list, because every column granted to `public` is a column published to the internet.

**Skip the rest of this section if your product has no unauthenticated surface.** What follows is one feature's design — a shared profile page at `/u/<id>` — and it is the longest passage in this guide. It is here because getting this wrong leaks data, not because every project needs it. The `add-permission` skill carries the same rules in short form if that is all you want.

The shipped example puts two independent switches on it, and both must be on:

- `auth_users.yaml` exposes an account to `public` when `metadata.publicProfile` is **not** `false` and there is no `deletedAt`. This is the master switch, and it is an opt-out: the page is on by default, so the absence of the flag means public and only the literal `false` withdraws it. A fresh account's `metadata` is JSON `null` rather than SQL NULL, and `'null'::jsonb` contains nothing, so it passes.
- `public_todos.yaml` gives the `public` role a select on rows that are `is_public` *and* whose owner, through the `user` relationship, satisfies the rule above.
- `storage_files.yaml` repeats that whole condition through the `todos` relationship. It has to: a relationship filter matches raw rows, it does not apply the related table's permission.
- `frontend/src/app/u/[id]/page.tsx` reads its **data** through `createAnonymousClient()`, never the session client. It does read the session for **identity** alone - whether the visitor is the owner, which decides if the empty state offers a way to fill it - and that is the only thing the session may be used for on a public page. The moment it reaches a query, Hasura answers as `user` and the row filter empties the page for signed-in visitors.
- `frontend/src/lib/profile.ts` is the UI's copy of the same rule. Read the flag through `isProfilePublic` rather than comparing it by hand, so the default lives in one place.
- `publicDisplayName`, not `displayName`, is what `/u/[id]` selects. Nhost auth defaults `display_name` to the signup address, so the raw column is the owner's email until they set a name over it; the `public` role is granted the `publicDisplayName` computed field instead, which withholds any name still shaped like an address. The shared page shows a name only when its owner chose one, and no name at all before that.
- `frontend/src/app/profile/actions.ts` sets the master switch with a read-merge-write, because `metadata` is one column shared with the soft-delete flow and a blind `_set` would drop `deletedAt`. Turning the page off writes `publicProfile: false`; turning it on deletes the key rather than writing `true`.

Rules to keep when extending this:

- Query public data with `createAnonymousClient()`. Using the session client makes Hasura answer as `user`, whose row filter hides other people's rows, so the page breaks for signed-in visitors only.
- Put the visibility rule in the permission, not in a `where` clause. A page that filters by hand is a page that can forget.
- Name the columns each role may read. Everything left off the `public` list is what cannot leak - among them `auth.users.email`, `auth.users.display_name`, `auth.users.metadata`, `auth.users.avatar_url`, and `todos.user_id`. Two of those look harmless and are not, for the same reason: both quietly contain the email address. `avatar_url`, for an account that never uploaded a photo, holds the Gravatar URL assigned at sign-up, which embeds `md5(lowercase(email))` - a bulk-harvestable pseudonym for the address; `/u/[id]` gets the picture instead from `storage.files`, which already serves it under the same public-and-not-deleted condition. `display_name` is worse, because auth defaults it to the address itself, in plaintext: `{ users { displayName } }` as `public` would have returned the project's address book. Both are replaced rather than simply dropped - the picture by the storage path, the name by the `publicDisplayName` computed field.
- A withheld column can often be replaced by a computed field rather than given up. `publicDisplayName` returns `display_name` only when it is plainly something its owner typed: it answers "what did this person choose to be called" without ever exposing the column the answer is derived from, which is the same move `hasPassword` makes for the password hash. Test the *shape* of such a value, not its equality with the thing you are hiding - see the next bullet. Grant such a field to `user` as well as `public` - `frontend/schema.graphql` is dumped with `--role user`, so a field granted only to `public` is missing from the dump and `pnpm codegen:types` fails on the document that selects it.
- Say what a role can still enumerate, and get the inventory right. This `public` rule has no row limit, so an anonymous `{ users { id createdAt publicDisplayName } }` walks every account whose page is on. That is ids, signup times, and any name an owner chose to publish - never an address, but not opaque ids either, since the computed field sits on this same permission. It is a list, and the README says so rather than implying the account table is private.
- Weigh a column's precision, not just whether it is a secret. `auth.users.created_at` is on the `public` list so the page can print "Since Sep 2026", but the column answers to the microsecond and the role gets that whether the page renders it or not. It is the one entry in that list making a trade rather than stating an obvious fact; if the trade is wrong for your project, drop the column and expose a coarser value as a computed field.
- `schema.graphql` is dumped for the `user` role, so a field readable there can still be unreadable as `public`. Adding one to `/u/[id]`'s query type-checks and then fails at runtime - check the `public` column list in `backend/nhost/metadata/` first.
- Do not offer a sharing control while the page is off. `TodoItem`'s eye and `WantFields`' visibility toggle are left out entirely in that state, because a control whose only effect is on a page that does not answer misreports what it did.
- After touching the `storage.files` select permission, confirm a private item's photo is a 404 anonymously and a shared one is a 200. Widening that rule exposes every private attachment at once.

## Accepting file uploads

Two paths, and the default is the direct one:

- Straight from the browser with the user's own token, as in `frontend/src/app/protected/TodoAttachment.tsx`. The `storage.files` insert permission for the `user` role authorizes it and restricts it to one bucket. Use this unless there is a reason not to.
- Through a serverless function with the admin secret, as in `backend/functions/avatar.ts`. Use this only when something must happen that the client cannot be trusted to do, such as resizing before storage.

## Example: accounts, storage and functions — the shipped profile page

**The rule this demonstrates.** Account data, file uploads and serverless functions meet in one place, and the division of labour is what to copy: the browser writes what it can be trusted to write, a function with the admin secret writes what it cannot, and a computed field answers a question about a row without ever exposing the column the answer is derived from.

`/profile` is that rule as one feature, and it exercises the parts of the stack todos does not:

- `backend/nhost/metadata/databases/default/tables/auth_users.yaml` lets the `user` role read its own row and update only `display_name` and `metadata`. `avatar_url` is written by the function as admin, so users cannot point it anywhere.
- `backend/nhost/migrations/default/1700000000001_avatars_bucket/` creates the bucket avatars land in; `storage_buckets.yaml` and `storage_files.yaml` track the storage tables. `storage_buckets.yaml` exposes the `avatars` and `todo-attachments` bucket rows (every bucket the template creates) to `public` and `user`, because `storage.files.bucket_id` is non-null and a file's related `bucket` would otherwise resolve to a permission-denied null and error out any query that selects it for a `todo-attachments` file. `storage_files.yaml` does not grant a plain bucket-scoped read: its `public` select is an `_or` of two conditions, neither one "the avatars bucket, unconditionally" - an avatar is readable unless its owner has turned their page off or the account is soft-deleted - the same opt-out test as everywhere else, `_not ... _contains {publicProfile: false}` - and a `todo-attachments` file is readable only through the same condition on its owning todo's `is_public` flag via the `todos` relationship. See "Example: data readable without a session" above before touching either permission.
- `backend/functions/avatar.ts` authenticates the caller against auth, resizes with jimp, stores through the storage REST API, and updates `avatarUrl` over GraphQL. The local runtime bundles each function with esbuild and native modules do not survive that, so use pure-JS dependencies (jimp, not sharp) in functions.
- `uploadAvatar` (`frontend/src/app/profile/actions.ts`) is a Server Action that takes a file, and Next.js caps a Server Action request body at 1 MB unless `next.config.ts` raises it: `frontend/next.config.ts` sets `experimental.serverActions.bodySizeLimit` to match `MAX_AVATAR_BYTES` (`frontend/src/lib/avatar.ts`, imported by both `actions.ts` and `AvatarPicker.tsx`). Any new Server Action that accepts a file needs the same config, or uploads over 1 MB fail with a raw 413 the action never gets to turn into a friendly error.
- `backend/nhost/migrations/default/1700000000002_auth_user_computed_fields/` holds the computed fields this template puts on `auth.users`, which share a migration because they share a reason: `auth.users` belongs to the auth service, so anything derived from a row the app may not expose has to arrive as a tracked function. `public.user_has_password` backs the `hasPassword` field, so the UI can tell "set a password" from "change password" without the hash ever leaving the database; `public.user_public_display_name` backs `publicDisplayName`, so a stranger sees a chosen name or nothing, never an email address. It withholds anything *shaped* like an address rather than merely comparing against the current one, and that distinction is the point: `UpdateUserConfirmChangeEmail` moves `email` without touching `display_name`, so an account that changed its address is left holding the previous one in a column no equality test against the new address can catch. The narrower branches cover the rest - a case-insensitive match (`email` is `citext`, `display_name` is `text`, so a bare comparison is case-sensitive), a whitespace-only name, and the phone number an SMS signup defaults to when there is no email to compare against at all.
- `backend/functions/auth-method.ts` answers, for one email address, which sign-in step to show. It needs the admin secret, so read the note in that file about what it does and does not reveal before copying the pattern. Before deploying this template publicly, put a rate limit in front of `/auth-method` (see "Before you deploy" in `README.md`) — nothing else in the shipped project does that for you.
- `frontend/src/app/profile/` holds the server page plus `ProfileCard` (avatar, name, email), `SecurityCard` (password) and `DeleteAccountCard`; each is a client component calling a server action in `actions.ts`.
- Account deletion is a soft delete: `deleteAccount` stamps `metadata.deletedAt` and signs out every session, and signing back in routes to `/restore`, which clears the mark. The proxy enforces that everywhere, so a marked account reaches only `/restore` and `/signin` until it is restored; a new page needs no check of its own. Update `metadata` with a read-merge-write `_set`; `_append` on a user whose metadata is JSON null produces an array and breaks sign-in.
- The template never purges. Erasing accounts once the grace period (`GRACE_DAYS` in `frontend/src/app/restore/page.tsx`) has passed is the project's responsibility, for example a scheduled job that hard-deletes users whose `metadata.deletedAt` is older than 30 days.

## Live data, and what this stack does not give you

The GraphQL API can serve changing data, within limits worth knowing before designing around them.

`frontend/schema.graphql` defines a `subscription_root`, and for every tracked table it exposes three fields: the list field (`todos`), the by-primary-key field (`todos_by_pk`), and a streaming field (`todos_stream`). The first two are Hasura **live queries**, and a live query is not a push. Hasura multiplexes it and re-runs it on a timer, and the generated `backend/nhost/nhost.toml` sets that timer with `liveQueriesMultiplexedRefetchInterval = 1000`; the setting's own documentation describes it as how often live queries are refetched. One second is therefore the floor on how stale a live query can be, and lowering it raises database load for every subscriber at once.

The template ships no subscription client. `frontend/package.json` has no `graphql-ws`, websocket or realtime dependency; the string `subscription` does not appear anywhere in `frontend/src/`; and the SDK's GraphQL client exposes a single `request()` returning a promise, with no subscribe method on it. Everything here is HTTP request/response with TanStack Query managing cache and refetch. Live data means adding a websocket client and wiring it up: nothing in this project is half-built towards it.

**The trap.** Finding `todos_stream` in the committed schema and concluding the project already has a live transport. Hasura generates a `_stream` field for every tracked table — there are four in this schema, for `todos`, `users`, `files` and `buckets` — and their presence says nothing about what the app uses. Shipping a poll while believing it is a push is the failure this paragraph exists to prevent.

What this is genuinely good for: changefeeds, notification badges, a shared list several people edit at human speed, anything where a second of staleness is invisible.

What it is not for: sub-100ms interaction, presence at pointer-move rate, and offline edits that must merge on reconnect. Those want a purpose-built layer — a CRDT such as Yjs or Automerge over a websocket provider — with Postgres as the snapshot store and this GraphQL API serving everything that is *not* the hot path: identity, membership, permissions, and the durable document. Do not try to make the HTTP data layer do it. The latency floor above is structural, not a tuning problem.

## Project conventions

- Server Components are the default. Any page that fetches server data uses `export const dynamic = 'force-dynamic'`.
- Create the server Nhost client per request with `createNhostClient()` from `@/lib/nhost/server`.
- Cookie writes belong in the proxy or server actions, never during Server Component rendering.
- `frontend/next.config.ts`'s `headers()` sends `X-Frame-Options`, a `frame-ancestors 'none'` CSP, `Referrer-Policy` and `X-Content-Type-Options` on every response, because the session cookie above is JS-readable and an XSS is a full account takeover without them. Keep this block when editing `next.config.ts` for another reason, such as the Server Actions body size limit.
- Protected routes read the session on the server and redirect to `/signin` when unauthenticated.
- Client-side GraphQL operations use the generated `graphql()` documents, `gqlRequest`, the browser `nhost` client, and TanStack Query.
- The browser `nhost` client (`@/lib/nhost/client`) is built with `withServerSideSessionMiddleware`, not the `createClient` default: it reads and attaches whatever token the proxy's session cookie holds, but never refreshes it itself. Wiring in the default client-side middleware would make it rotate the same single-use refresh token the proxy already rotates on every navigation, and the two would race with nothing to arbitrate the loser's session getting wiped. Do not add `sessionRefreshMiddleware` (or switch back to `createClient`) to this client for that reason.
- Use absolute frontend imports through `@/` and merge class names with `cn()` from `@/lib/utils`.
- Wrap network calls in explicit error handling so the UI fails gracefully when the backend is unavailable.
- Auth emails that link back into the app (password reset, email change) build `redirectTo` from `appOrigin()` in `@/lib/nhost/env`, which reads the configured `NEXT_PUBLIC_APP_ORIGIN`. Never derive it from `Host` or `X-Forwarded-Host`: the sender controls those, so it would let anyone aim someone else's reset link at a host they own.
- Those links come back as `?refreshToken=...&type=...`, which the proxy redeems into the session cookie before redirecting to the same URL without them. It strips those parameters whenever they are present, not only when it redeemed them: a token it declined was never spent, so leaving it in the URL would leave a live credential in history and bookmarks.
- Redemption takes three things: a `type` the auth service actually emits, a path in `LINK_REDEMPTION_PATHS` (`/profile`, `/reset-password`), and no signed-in session belonging to somebody else. Without the last one a crafted link on an allowed path would still swap a visitor's session for the attacker's, and everything they wrote next would land in that account. Point a new auth email at one of those paths, or add the path to that list.
- `LINK_TYPES` holds the `TicketType` values the verify redirect carries (`emailConfirmChange`, `passwordlessEmail`, `passwordReset`, `verifyEmail`), which are **not** the `LinkType` names used to request an email — a verification link arrives as `verifyEmail`, not `emailVerify`. Adding a flow means adding its ticket type here, or the link is silently refused and the visitor lands anonymous.
- Changing a password revokes the account's refresh tokens, so `changePassword` signs back in on the new password. Anything else that rotates credentials has to do the same or it logs out the person who just used it.
- `changePassword` and `changeEmail` both decide for themselves whether re-authentication is needed, through the shared `requireCurrentPasswordProof`: it reads `hasPassword` from the backend and requires `currentPassword` when the account has one (`changePassword` also accepts a password-reset grant naming this same account). An account with no password has none to prove, so `requireCurrentPasswordProof` instead requires a code from `sendReauthCode`, verified with `verifySignInOTPEmail` — the same "this browser controls the mailbox" proof the reset-link grant relies on, so a stolen session cannot skip it either. Never gate a sensitive action on an argument the client chooses to send. `changeUserEmail` notifies only the new address, never the old one, so without this a stolen session could redirect the account's login identity to a mailbox the attacker controls and reach "forgot password" without ever knowing the current password - every action that changes how someone signs in needs the same proof.
- The grant cookie is `httpOnly`, carries the id of the account the redeemed link signed in, and is only honoured for that account; it is cleared on sign-out and on every sign-in. Be precise about what it proves: that this browser redeemed a reset link **for this account**, not that anyone controls its mailbox. Because the session cookie is readable by JS, a holder of a live refresh token can mint one for whatever account that token names, without any email. Treat that as the escalation it is: a stolen session cannot otherwise change the password, because `changePassword` demands proof it does not carry — the current password, or a code just emailed to the account when it has none — so the grant path is what turns a stolen session into a permanent takeover — changing the password revokes every other refresh token and locks the real owner out. Closing it needs the auth service's PKCE flow, whose `code` is bound to the ticket.
- Sign-in asks for the email first and then shows the step that account actually uses, so a new page must not assume a password exists. `hasPassword` is the flag for that.
- Read the backend subdomain and region through `nhostSubdomain()` / `nhostRegion()` from `@/lib/nhost/env`. `NEXT_PUBLIC_NHOST_SUBDOMAIN` and `NEXT_PUBLIC_NHOST_REGION` are the only pair, shared by the browser and the server; do not add a server-only pair, which would let the two halves target different backends.
- Next.js inlines `NEXT_PUBLIC_*` at build time, so those two variables must be set before `next build`; setting them on the running host has no effect and the build stays pointed at the local stack.
- Never commit real values from `backend/.secrets` or frontend environment files. `frontend/.gitignore` ignores every `.env*` except `.env.example`, and the project-root `.gitignore` covers `.secrets` and `.nhost`.

## Key commands

From `backend/`:

- `nhost up` starts the local stack and applies pending migrations and metadata.
- `nhost down` stops the stack.
- `nhost logs` shows local service logs.

From `frontend/`:

- `pnpm dev` starts the app at <http://localhost:3000>.
- `pnpm codegen` refreshes `schema.graphql` and `src/gql/` from the running local backend.
- `pnpm codegen:types` regenerates types offline from the committed schema.
- `pnpm lint`, `pnpm format`, `pnpm test`, and `pnpm build` validate the app.

## Optional MCP bonus

The optional `.mcp.json` can start the Nhost MCP server for assistants that support it. Setup, skills, codegen, and every required workflow work without MCP.

It sets `NHOST_MCP_CONFIG_FILE` to `backend/.nhost/mcp-nhost.toml`, resolved from the directory the client starts the server in, which is the project root. Do not swap that for a `cwd` key: clients drop it silently.

Until that config file exists, the server runs on its built-in default, which grants the local admin secret, unrestricted queries and mutations, and metadata management. That bypasses row-level permissions, so it is not read-only inspection. Run `nhost mcp config` from `backend/` to scope it, and point it at a local project only.
