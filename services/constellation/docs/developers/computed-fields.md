# PostgreSQL computed fields: alpha contract inventory

Phase 2 fixture/oracle: the existing `integration/nhost/nhost.toml` image (`nhost/graphql-engine` v2.48.10-ce), `cf_select` and `cf_predicates` sources on `local`. The two sources are independent of `default`, `customized` and `other`; `cf_predicates` has **no computed predicate permissions at startup**. Use `integration/computedfields/testdata/{contract,predicate_permissions,inconsistent_contract,metadata}.json` as checked-in Constellation-only expectations. The `connector/sql` fixture tests build isolated test databases from the **same** Nhost migration and seed used by integration, check that the metadata JSON matches the tracked YAML tables, replay each SQL/DDL variant and predicate SQL without Hasura, and validate recorded role SDL and GraphQL expectation shapes. They do not yet assert Hasura-style inconsistency classification or execute the computed GraphQL expectations: later phases must add those assertions when reconciliation and execution become available. `TestComputedFieldReference` remains a small live connectivity/control comparison, not the regression oracle for these cases.

## Observed accepted forms and behavior

- Fully qualified, stable SQL functions taking the table row as their first argument: text, numeric with an optional extra integer argument, JSONB and `SETOF` tracked rows. Explicit `table_argument` also accepts a row argument **after** another argument (`item_second(multiplier, item)` yielded `25` for `multiplier: 2`). Row-bound fields are nullable even when the source columns are non-null; JSONB fields additionally accept a `path` selection argument. The optional multiplier is an input field of `item_score_cf_select_items_args` (`Int`, nullable); the function's SQL default is used when omitted (`12.5` for item 1). `item_second(args: {})` instead returns `not-supported`: `Non default arguments cannot be omitted`. `item_second` requires `item_second_cf_select_items_args!`, while `item_score` accepts an optional args object.
- Admin and `cf_reader` see the scalar and table-valued fields; `cf_no_grant` sees only its permitted columns and neither computed `_args` type. The nullable field types, non-null elements of the nullable `item_tags` list, `item_payload(path: String)`, both argument input types, boolean/order inputs and denied-role absences are recorded per role in `contract.json`. `item_label`/`item_payload` occur in boolean expressions and ordering; `item_tags` occurs in boolean expressions and `item_tags_aggregate` ordering. The argument-bearing `item_score` does **not** occur in either boolean or order inputs. `item_tags` list selection has target-table `where`, `order_by`, `distinct_on`, `limit` and `offset`; target permissions derive its visibility. Numeric arguments, JSONB selections and a JSONB `_contains` predicate returned the checked-in response values. Admin `update_cf_select_items.returning` evaluated the computed scalar, argument and table selection on the updated row; its fixture label was restored after the probe.
- Explicit scalar select grants are accepted. An explicit select grant for `item_tags` is **inconsistent**: table-returning computed select access is inferred from permissions on `cf_select.tags`. A `cf_no_grant` selection of `item_label` fails GraphQL validation, rather than returning null.
- A separate `cf_predicate_guard` role with `rule_visible: {_eq: true}` select filter returned only rule `1`. The same predicate was accepted in update `filter` and `check` and insert `check` metadata. These permissions are checked in as a *non-startup* fixture until Constellation enforces them. A computed scalar as a `to_source` remote relationship join key (`field_mapping: {item_label: label}`) was accepted by `replace_metadata` with no inconsistency; query execution, permission and argument-bearing join shapes still require Phase 12 probes.

## Observed rejected/inconsistent forms

- `pg_add_computed_field` referring to a missing function failed with `invalid-configuration` and did not change export metadata. Adding a second overload of an existing tracked computed function made its field inconsistent (`computed_field`), and its explicit role grant inconsistent (`select_permission`); Hasura reports that overloaded functions are not supported. A distinct field name may refer to the same SQL function (the `column_collision` alias was accepted); name/type collisions with actual columns require a separate probe, not extrapolation from that result.
- Dropping `cf_predicates.rule_visible(cf_predicates.rules)` then reloading metadata marked both the field and its `cf_reader` grant inconsistent. For that role `__type(name:"cf_predicates_rules")` became null and querying the root yielded `validation-failed`. Restoring the exact function and reloading restored consistency.
- Replacing metadata with `allow_inconsistent_metadata: true` and a select filter referencing `missing_computed` marked only that `select_permission` inconsistent. The affected role lost `cf_predicates_rules` from its SDL; an unaffected source remained present. Do not remove a failing filter and retain its role permission. Constellation currently also removes the affected source/role on this invalid filter; this is **not** evidence that it enforces valid computed filters.

The destructive probes ran **serially**, after an `export_metadata` snapshot; each restored function DDL and `replace_metadata` in a finally block, checked `get_inconsistent_metadata` was empty, and awaited the existing DB-backed Constellation's metadata resource version on replacement before switching the same container back to file metadata. Do not overlap these probes with integration query tests, and do not add their invalid entries to startup YAML.

## Remaining investigation (not classified as supported/rejected yet)

Other volatility modes, row/return signatures, collision cases, session arguments, insert/delete/nested mutation `returning` and checks on actual writes, subscriptions, aggregate/grouped-aggregate row contexts, cross-source and remote-schema join execution and errors, numeric/JSON edge cases, customization, and SQL function errors need targeted alpha probes before exposure. Each accepted case needs its own independent expected metadata/SDL/SQL/result/error/permission regression; the live comparison remains deliberately small. Constellation retains computed definitions and grants from Hasura metadata and native TOML, but does not serve them: **no computed GraphQL fields are exposed**. Do not describe these observations as current product support.
