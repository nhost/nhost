# PostgreSQL computed fields: alpha contract inventory

## Remote join-key contract (Phase 13)

The existing Hasura v2.50.3-ce oracle accepts no-user-argument scalar LHS
keys: `item_label` self object/array and cross-source object (positive text
matches), `item_payload` self and cross-source object with a JSONB target,
and a text-valued computed team ID joined to remote `team(id: ID!)`. A
session-bound variant joins two distinct team IDs for two session cohorts.
Hasura rejects `item_score`/`item_second` (user arguments) and `item_tags`
(table result) at metadata validation. It accepts a JSONB-object→remote
`ID!` definition but execution fails GraphQL ID coercion; do not infer
support from metadata consistency alone. Constellation excludes every
JSON/JSONB computed LHS key toward remote schemas, regardless of argument type;
JSONB source joins to JSONB target columns bind/stitch objects, strings,
numbers and arrays as distinct JSON values. Constellation requires an explicit
per-role LHS computed select grant for any of these joins (admin is implicit).
Hasura joins denied keys; that behavior is intentionally not reproduced.
The source's function runs as a phantom selection under the caller's session;
its response key is removed after stitching. For a JSON `path` selection, a
separate full-value phantom must be injected rather than reusing that path's
projection. For computed `to_source` keys, target join-column select access is required
in Constellation even though Hasura joins through denied columns (a hidden-value
equality oracle); target row filters still apply. Physical-key relationships do not
use the computed-key grant or target-column gates. JSONB targets bind
typed JSON values for object/array joins, including physical keys whose target column is role-hidden; JSONB array `_aggregate` siblings
bind and stitch typed keys for computed and physical JSONB keys. PostgreSQL `json` targets lack `json = json`, so ordinary and grouped joins into them fail at execution, as in Hasura’s equality join. GeoJSON object
keys are also JSON-encoded, fixing physical geometry joins. Hasura rejects remote relationships in subscriptions, and
the WebSocket path must reject them before polling.


Phase 2 fixture/oracle: the existing `integration/nhost/nhost.toml` image (`nhost/graphql-engine` v2.50.3-ce; initial inventory ran on v2.48.10-ce), `cf_select` and `cf_predicates` sources on `local`. The two sources are independent of `default`, `customized` and `other`; `cf_predicates` has a startup `cf_predicate_guard` scalar select filter and insert check. Use `integration/computedfields/testdata/{contract,predicate_permissions,inconsistent_contract,metadata}.json` as checked-in Constellation-only expectations. The `connector/sql` fixture tests build isolated test databases from the **same** Nhost migration and seed used by integration, check that the metadata JSON matches the tracked YAML tables, replay each SQL/DDL variant and predicate SQL without Hasura, and validate recorded role SDL and GraphQL expectation shapes. Reconciliation tests now assert computed-field and known computed-permission inconsistency classification. PostgreSQL scalar selection and user-input capabilities are enabled for queries, mutation `returning` and conditions (including conflicts), live/stream subscriptions, aggregate/grouped rows and cross-source/remote-schema-to-database results. Only argument-free scalar fields occur in row boolean/order inputs, including JSONB fields whose selection accepts `path`. Hasura includes no **scalar** computed fields in aggregate-order inputs. All ten aggregate field output types include eligible computed returns; output arguments and declared return types are retained even when physical column aggregates use `Float`. PostgreSQL table-valued `SETOF` selections are enabled when the target table has select access; argument-free scalar permissions execute in role filters/checks. Argument-free table functions now execute in row boolean EXISTS and `<field>_aggregate` ordering and in select/update/delete filters and insert/update checks. User inputs apply returned-table select permissions, including the target row filter; metadata predicates run independently of target select access. A serialized v2.50.3-ce probe with target filter `label = one` returned no items for `where: {item_tags: {label: {_eq: two}}}` (admin returned item 1). With target filter `label = three`, aggregate count-desc ordering returned items `[2, 1]` (admin `[1, 2]`). Both changes were restored from `export_metadata` and consistency checked; static filtered roles now pin these outcomes in the live sanity suite. The older v2.48.10-ce image did not enforce the target row filter for user table EXISTS, so do not use it as the security contract. Unnamed non-row SQL arguments are exposed as `arg_N`, counting only unnamed user inputs after removing the row and session arguments; named inputs do not advance the counter (verified against the existing Nhost Hasura v2.48.10-ce instance). This computed-only mapping does not change the older tracked-root `FunctionArgument.GraphQLName(index)` positional numbering; align that separately. The PostgreSQL-only PostGIS geometry/geography constructors and JSON output conversion share existing column helpers; testdb verifies input/output coercion, and their live Hasura behavior was confirmed for SRID 4326. GraphQL validation error paths use field names (including customized prefix/suffix/namespace roots and remote-relationship prefixes), while SQL result/stitching paths continue to use response aliases. An unset variable inside a computed `args` object binds a typed SQL NULL, distinct from omitting the key and using the SQL default. Quoted JSON paths reject lone surrogate escapes; keys containing NUL return null without binding NUL text. Keep the function call under a strict `#> NULL::text[]` lookup so client/session argument placeholders remain referenced, even when another computed selection follows. For a 4326 geometry, `ST_AsGeoJSON(value, 15, 4)` includes a long `crs` name; test the full payload rather than assuming only `type` and `coordinates`. `TestComputedFieldReference` includes representative live scalar/table selection, scalar user-input/aggregate-output and table predicate/order comparisons but remains a small sanity comparison, not the regression oracle for these cases.

Local verification caveat: Nix's `make check` filters untracked new source files out of its copied tree, so it cannot compile this phase until those files enter the Git index; direct `go test`, `golines` and `golangci-lint` still exercise the working tree without staging. For a locally built service used by `TestComputedFieldReference`, inject a nonempty `main.Version` via `go build -ldflags '-X main.Version=...'` (plain `go run` returns an empty `/v1/version`). Preserve the trailing slash in `CONSTELLATION_METADATA_PATH` when pointing at a metadata directory: its loader resolves includes relative to `filepath.Dir` of that path.

the later v2.50.3-ce filtered-target probe above did. The metadata was restored from

restored; computed references inside relationship-aggregate **permission**
filters remain fail-closed, unlike user-facing aggregate predicates.

## Observed accepted forms and behavior

- Fully qualified, stable SQL functions taking the table row as their first argument: text, numeric with an optional extra integer argument, JSONB and `SETOF` tracked rows. Explicit `table_argument` also accepts a row argument **after** another argument (`item_second(multiplier, item)` yielded `25` for `multiplier: 2`). Row-bound fields are nullable even when the source columns are non-null; JSONB fields additionally accept a `path` selection argument. The optional multiplier is an input field of `item_score_cf_select_items_args` (`Int`, nullable); the function's SQL default is used when omitted (`12.5` for item 1). `item_second(args: {})` instead returns `not-supported`: `Non default arguments cannot be omitted`. `item_second` requires `item_second_cf_select_items_args!`, while `item_score` accepts an optional args object. **Gotcha:** Hasura leaves the `multiplier` field *inside* both input objects nullable (`Int`), even for the required SQL argument; enforce missing required values during function-call construction, not by changing the field to `Int!` (which changes role SDL). SQL must reconstruct the entire physical row as a schema-qualified table composite from CTE/function aliases; casting an anonymous or role-projected row fails or hides values needed by the function.
- Admin and `cf_reader` see the scalar and table-valued fields; `cf_no_grant` sees only its permitted columns and neither computed `_args` type. The nullable field types, non-null elements of the nullable `item_tags` list, `item_payload(path: String)`, both argument input types, boolean/order inputs and denied-role absences are recorded per role in `contract.json`. `item_label`/`item_payload` occur in boolean expressions and ordering; `item_tags` occurs in boolean expressions and `item_tags_aggregate` ordering. The argument-bearing `item_score` does **not** occur in either boolean or order inputs. `item_tags` list selection has target-table `where`, `order_by`, `distinct_on`, `limit` and `offset`; target permissions derive its visibility. Hasura has no `item_tags_aggregate` selection sibling; its separately recorded `item_tags_aggregate` **input** executes as a correlated aggregate order. A serialized nullable-composite `SETOF` function probe returned `[{id: null}]` for admin and `cf_reader`, not `null` or `[]`; metadata and DDL were restored and Hasura consistency checked. The Constellation-only testdb suite pins the same shape, empty collections, SQL errors, nested selections and target permissions. Numeric arguments, JSONB selections and a JSONB `_contains` predicate returned the checked-in response values. Admin `update_cf_select_items.returning` evaluated the computed scalar, argument and table selection on the updated row; its fixture label was restored after the probe.
- Explicit scalar select grants are accepted. An explicit select grant for `item_tags` is **inconsistent**: table-returning computed select access is inferred from permissions on `cf_select.tags`. A `cf_no_grant` selection of `item_label` fails GraphQL validation, rather than returning null.
- A separate `cf_predicate_guard` role with `rule_visible: {_eq: true}` select filter returned only rule `1`. The same predicate was accepted in update `filter` and `check` and insert `check` metadata. The select filter and insert check now run from startup metadata; other metadata probe variants remain isolated. A computed scalar as a `to_source` remote relationship join key (`field_mapping: {item_label: label}`) was accepted by `replace_metadata` with no inconsistency; positive join execution and per-role permissions are classified above; argument-bearing and table-valued LHS keys were rejected at metadata validation.

## Observed rejected/inconsistent forms

- `pg_add_computed_field` referring to a missing function failed with `invalid-configuration` and did not change export metadata. Adding a second overload of an existing tracked computed function made its field inconsistent (`computed_field`), and its explicit role grant inconsistent (`select_permission`); Hasura reports that overloaded functions are not supported. A distinct field name may refer to the same SQL function (the `column_collision` alias was accepted and now has an independent served-SDL/data test). The separate collision/grant matrix is classified below; do not infer it from the alias case.
- Dropping `cf_predicates.rule_visible(cf_predicates.rules)` then reloading metadata marked both the field and its `cf_reader` grant inconsistent. For that role `__type(name:"cf_predicates_rules")` became null and querying the root yielded `validation-failed`. Restoring the exact function and reloading restored consistency.
- Replacing metadata with `allow_inconsistent_metadata: true` and a select filter referencing `missing_computed` marked only that `select_permission` inconsistent. The affected role lost `cf_predicates_rules` from its SDL; an unaffected source remained present. Do not remove a failing filter and retain its role permission. Constellation retains its source-wide root-construction failure for this unidentifiable unknown key (also reproduced by a column-only unknown-key control). This operator-approved invalid-key divergence is **not** supported computed-field parity. A filter key identified by a definition or grant is removed with its whole permission if invalid or unexecutable; executable argument-free scalar predicates now run without a select grant.

The destructive probes ran **serially**, after an `export_metadata` snapshot; each restored function DDL and `replace_metadata` in a finally block, checked `get_inconsistent_metadata` was empty, and awaited the existing DB-backed Constellation's metadata resource version on replacement before switching the same container back to file metadata. Do not overlap these probes with integration query tests, and do not add their invalid entries to startup YAML.

## Remaining investigation and bounded unsupported forms

Domain/enum/range/multirange scalar returns were rejected as non-BASE by serialized `pg_add_computed_field` probes against the existing Nhost Hasura; Constellation marks their definitions invalid and revokes select permissions granting them. Supported domain, enum, composite, range, multirange and built-in array **arguments** are exposed as string-only custom scalars (`<type>_scalar` for composites) with parameterized schema-qualified casts. `connector/sql/computed_custom_arguments_test.go` checks role SDL, data, parse/SQL errors, aggregate and mutation returning independently on isolated testdb. Selected serialized Hasura v2.50.3-ce observations are checked in at `integration/computedfields/testdata/phase14-oracle.json` (no metadata snapshot or connection details): it exposes non-public custom argument fields but fails string, null and variable-valued requests with `type "…" does not exist`, whereas a public-domain control executes and reports domain-check/invalid-integer errors. GraphQL enum-token literals resolve to string names; numeric/list custom inputs fail parsing. Catalog array identity also applies to user-defined enum arrays and rejects non-string input at the argument path. The operator approved only qualified successful execution for accepted non-public types; the observed error does not establish Hasura's internal cause. PostgreSQL base types, including extension types such as `citext` and `vector` outside `pg_catalog`, are accepted by kind rather than schema. Single tracked-table and `SETOF text` return signatures are independently pinned in `connector/sql/computed_return_signatures_test.go`; `SETOF numeric` and mutation-returning cardinality have isolated `connector/sql/computed_numeric_return_test.go` coverage: a NULL/missing single composite creates an all-null list element unless the target row filter excludes it; a `SETOF` scalar can produce null parent rows, duplicate rows in `order_by`, a multi-row scalar-subquery error and aggregate maxima. Hasura rejects `text[]` returns as non-BASE; an invalid explicit grant revokes only its role's select permission. Classified: physical/custom-name/object/array/to_source collisions with and without grants, custom-scalar name collisions, and nullable `to_remote_schema` text keys (see table above). The serialized disposable-only oracle classified numeric `SETOF` direct/where/order/max, scalar/table mutation returning and the exact aggregate sibling collision, with independent restoration checks. The explicitly enabled scalar `SETOF` kinds are `pg_catalog.text`, `numeric`, `int4`, `float8`, `bool`, `date`, `uuid`, `jsonb` and installed `public.citext`; `computed_setof_kinds_test.go` pins each on its own testdb, and combined aggregates expand count, physical columns, computed operands and nodes from one row source (including nested and grouped per-key windows, with multiple SETOF operands in lockstep) instead of only fixing per-parent average/variance weighting: even zero/one-row `where` requests fail at the database; ordering drops zero-row parents and duplicates multi-row parents; direct zero yields a null parent and direct multi-row fails. Scalar SETOF returning zero yields a null single-object result or a null element for each affected collection row while successful writes persist. Multi-row results raise PostgreSQL 21000 and roll back all writes in the same-source mutation; production GraphQL errors remain sanitized under the inherited approval. A single-composite table return missing its row yields an all-null list element for unrestricted roles. **Still bounded:** vector, spatial, array and other untested BASE scalar `SETOF` kinds are not inferred from the disposable probe. A disposable public enum and enum-array were independently Hasura-probed: scalar bare `happy` and quoted `"happy"` succeed, array bare `happy` is a malformed-array database error while quoted `"{happy}"` succeeds; numeric/list parse-fail and invalid labels fail at the database, with null/default outcomes pinned. `connector/sql/computed_public_enum_arguments_test.go` uses an isolated public enum testdb; the earlier p6 nonpublic enum only proves parsing (runtime type-not-found), not successful nonpublic Hasura execution. The independent metadata/role/SDL and query tests do not turn any of these unknowns into a blanket parity claim. `IMMUTABLE` execution was accepted; `VOLATILE` definition and invalid grant were rejected by the pinned oracle. `connector/sql/computed_custom_arguments_test.go` now pins immutable served SDL/data, and `reconcile_computed_validation_internal_test.go` pins volatile field/grant revocation. These are not approved parity exceptions; no alpha-closure claim follows. Argument-free scalar filters/checks run against physical rows with earlier dependent writes visible on the ordered executor; table-valued selections use the shared collection builder over a correlated function source and target permissions, with table predicate/order inputs and role predicates using the correlated function source. JSON selection `path` uses Hasura grammar (`$`, dot keys, bracket indices and quoted bracket keys) and binds parsed segments as `text[]`; in Go raw-string test cases use one backslash for a JSONPath Unicode escape (`["\u0073tatus"]`), not two (which means a literal backslash in the key). Explicit `args: null` and `path: null` return argument-specific validation errors; omitting either argument entirely preserves default/full JSON behavior. Error paths use GraphQL names even when SQL response keys use aliases. The pre-existing jsonb **column** `path` implementation is separately tracked, not changed by the computed-field parser. Serialized Hasura probes established that date, timestamptz and uuid computed returns occur in `min`/`max`; boolean and JSONB do not, while Hasura rejected a `time` computed return as non-BASE. PostgreSQL in the fixture has no `min(uuid)`: Hasura advertises the uuid aggregate field but returns a database-query error with SQLSTATE `42883` when selected. Constellation pins the same SQLSTATE in an independent testdb regression; do not describe uuid aggregate **results** as working without a PostgreSQL implementation. Numeric computed returns occur in the other eight aggregate output types, including `sum`, `avg` and the variance family. Hasura retains the function return type (numeric in the fixture) for computed `avg`/variance fields, unlike physical column `Float`. Constellation follows this fixed computed-output eligibility, separately from its dynamically discovered column aggregate support documented in `KNOWN_DIFFERENCES.md`. A temporary array relationship targeting computed items confirmed Hasura omits even argument-free computed fields from aggregate-order inputs; the probe restored metadata equality and consistency before ending. Each accepted case needs its own independent expected metadata/SDL/SQL/result/error/permission regression; the live comparison remains deliberately small. Constellation retains computed definitions and grants from Hasura metadata and native TOML. PostgreSQL scalar selections, argument-free user predicates/order and eligible aggregate outputs are served with supported argument types. Table-valued selections, argument-free row boolean/order inputs and role predicates are supported on PostgreSQL; unexecutable computed references remain fail-closed.
